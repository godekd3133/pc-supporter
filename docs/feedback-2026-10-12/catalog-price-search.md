# 2026-10-12 그래픽카드 가격·검색·필터 변경

## 확인한 문제

- 가격 갱신 우선 큐는 GPU 모델·VRAM별로 최저가 상품 1개와 판매처 없는 상품 1개만 선택했다. 같은 GPU의 다른 제조사·유통사 상품은 일반 부품 순환 큐에 남았다.
- `price_refresh_attempts.attempted_at`은 실패도 기록한다. 이 값은 순환 순서를 정할 때 필요하지만, 성공한 가격 확인일과는 다르다.
- 목록 조회 중 가격 재확인 큐는 수집 작업이 바쁘거나 네트워크 오류가 나면 상품을 꺼낸 채 버렸다. 그 상태를 확인할 수 없었다.
- 검색은 원문 소문자 substring 비교였다. `5060ti`와 `5060 Ti`가 달랐다.
- 공개 검색과 관리자 생성기 설정이 같은 세부 필터 목록을 사용했다.

## 변경

1. 국내 RTX 50·RX 90 시리즈와 지정 MSI 3050·AFOX 580 계열의 **모든 상품**을 우선 순환한다. 모델 최저가 한 상품에 제한하지 않는다. 기본 100건 갱신 중 최대 80건은 이 큐, 최소 20건은 다른 부품 큐다. 한 큐가 부족하면 남은 자리를 다른 큐가 사용한다.
2. 성공한 가격·판매처 없음 관측은 3시간, 실패한 조회는 1시간의 재시도 간격을 적용한다. 실패는 `priceCheckedAt`을 바꾸지 않는다. 최근 판매처 없음 상태도 가격 확인으로 인정하되 예전 양수 확인일을 덮어쓰지 않는다.
3. 조회 중 갱신이 바쁘거나 실패하면 상품을 대기 큐에 유지한다. 다음 목록 조회에서 재시도한다. 바쁨은 1분, 실패는 5분 간격이다. 큐 크기·성공·실패·지연 수와 최근 오류를 `stalePriceRefreshStatus()`와 서버 로그로 확인한다. **조회 API는 응답을 막지 않으므로 최초 응답이 반드시 최신 가격이라는 의미는 아니다.**
4. 새 가격/판매처 없음 확인 없이 옛 가격만 돌아온 경우는 성공으로 처리하지 않는다. 기존 상품코드·이름 확인, 판매처 없음에 대한 가격 제거, 오래된 스냅샷의 가격 부활 방지는 유지한다.
5. 서버 검색과 브라우저 캐시 검색이 공통 정규화를 사용한다. `5060ti`, `5060 ti`, `RTX5060TI`를 같은 모델로 검색한다. 완전한 모델 `5060`은 `5060ti`를 함께 찾지 않는다. 일반 상품명의 단어 사이 공백은 임의로 제거하지 않는다.
6. 공개 GPU 세부 조건에서 메모리 타입·부스트 클럭·로우프로파일·소비 전력·권장 파워·카드 길이를 제거한다. 관리자 설정과 저장된 관리자 조건은 보존한다.
7. 공개 그래픽카드 두께에 `~41mm`, `~51mm`, `~61mm` 체크박스를 추가한다. 상한을 포함한다. 같은 항목 다중 선택은 OR이므로 41과 51을 선택하면 51mm 이하가 된다. 두께 정보가 없는 상품은 해당 조건 선택 시 제외한다. 두께 최소/최대 숫자 입력은 표시하지 않는다.

## 배포 후 운영 절차 (통합 담당 실행)

준비한 `scripts/refresh-gaming-gpu-prices.mjs`는 이 담당 세션에서 원격 실행하지 않았다. 먼저 새 코드의 타입 검사·빌드·배포를 완료해야 한다. 배포 전 버전은 기존 대표 상품 큐이므로 이 절차를 반복해도 전체 상품의 갱신을 보장하지 않는다.

실행 위치는 Azure의 `/opt/pc-supporter/current`다. 스크립트가 배포 묶음에 포함되지 않으면 통합 담당이 별도로 그 `scripts/`에 복사한다. 로그에 비밀번호·쿠키·DB URL을 기록하지 않는다.

```sh
sudo node scripts/refresh-gaming-gpu-prices.mjs --audit-only --output=/opt/pc-supporter/backups/gpu-prices-20261012-before.json
sudo node scripts/refresh-gaming-gpu-prices.mjs --refresh --max-rounds=8 --output=/opt/pc-supporter/backups/gpu-prices-20261012-after.json
```

- 기본값은 읽기 전용 감사다. `--refresh`가 있을 때만 갱신 작업을 시작한다.
- 확인 대상은 국내 RTX 50, RX 90, MSI 3050, AFOX 580 중 상품코드/상세 URL이 있는 다나와 상품이다. 현재 가격이 없는 상품도 포함한다.
- 가격과 판매처 없음 확인의 마지막 시각으로 12시간 초과를 구분한다. `updatedAt`이나 실패한 `attempted_at`은 가격 확인 시각으로 쓰지 않는다.
- API가 허용하는 최댓값 `coreLimit=100`을 사용한다. 우선 GPU 최대 80건과 일반 부품 최소 20건이 순환한다. 주변 부품은 API 허용 최솟값 `accessoryLimit=1`, 요청 간격은 기존 기본값 1,200ms다.
- 이미 대기/실행 중인 가격 작업이 있으면 완료를 기다린다. 이후 작업도 하나씩 시작하고 완료 후 다음 작업을 시작한다. 409 응답은 다시 확인한다. 기존 작업을 강제 종료하지 않는다.
- 상품별 기존/최종 가격·마지막 확인일·`no_offers`/`price_unknown`·stale 상태를 보고서에 기록한다. 작업 실패 수와 상품의 가격 부재는 별개다.
- 최신 확인 비율이 나아지지 않으면 멈춘다. 일부 오래된 상품이 남으면 exit 2다. 이를 전체 갱신 완료로 보고하면 안 된다. 실패/수집 지연 상품은 원인을 확인하고 후속 재시도가 필요하다.
- 관리자 상태 응답의 `servedPriceRefresh`에서 조회 기반 큐의 대기·진행·성공·실패·지연과 최근 오류를 확인한다. 이 큐 관측값은 API 프로세스 단위이며 재시작하면 초기화된다. 정기 가격 작업의 DB 저장 상태는 별도로 유지한다.

추가 회귀 항목: 최근 사양 수정일이 가격 확인일을 대체하지 않도록 수정했다. 후속 `catalog-price-search-freshness-final-test.log`에 검증 결과를 기록한다.

공개 필터 정의는 `shared/public-catalog-filters.ts`에 분리했다. 관리자 생성기 필터를 읽는 첫 화면에서 공개 GPU 필터의 초기화 코드까지 포함하지 않도록 한 변경이다. 이전 공유 모듈에서 재내보내지 않으며, 서버 공개 검색과 카탈로그/선택기 화면이 새 모듈을 직접 사용한다. 타입 검사·첫 화면 번들 크기 검사는 통합 빌드에서 확인한다.

## 지속 갱신 주기 검토

전체 가격 재확인을 한 번만 실행하면 다시 오래된 상태가 된다. 추천 대상 GPU 506개, 우선 GPU 80건/회 기준으로 한 바퀴에 필요한 슬롯은 `ceil(506 / 80) = 7`이다.

| 설정 | 정상 작업 기준 GPU 1회전 | 주변 부품 하루 처리량 |
| --- | --- | ---: |
| 3시간, core 100, 주변 부품 500 | 최대 약 21시간 + 회당 처리시간 | 4,000건 |

2026-10-12 실제 완료한 예약 작업 600건은 03:49:05~04:06:21 UTC, **17분 16초** 걸렸다. 수동 작업 101건은 09:38:42~09:41:41 UTC, **2분 59초** 걸렸다. 같은 관측 속도를 단순 적용하면 270건 작업은 약 8분이다. 이는 추정이며 응답 지연과 오류가 있으면 달라진다.

```text

PRICE_REFRESH_DELAY_MS=1200
```

코드는 1시간 주기와 위 제한 값을 이미 지원한다. 전용 worker가 현재 작업 완료를 기다린 뒤 다음 작업을 가져와 동시 가격 갱신을 하지 않는다. 수집 데이터의 공유 lease도 별도로 적용한다. 동일 UTC 시간 슬롯은 DB idempotency key로 중복 생성하지 않는다. **서로 다른 시간 슬롯의 대기 작업까지 모두 하나로 합치는 것은 아니다.** 작업이 길어져 쌓인 이전 예약 슬롯은 실행 전에 `STALE_SCHEDULE_SLOT`로 건너뛴다.

위 7시간은 정상 처리 중 순환 주기의 보수적 산정이다. 최신 가격 확인을 무조건 보장하는 SLA가 아니다. 네트워크가 계속 실패하면 확인일은 유지돼 오래된 상태로 남는다. 기본 요청 timeout 12초·1회 재시도·350ms 대기와 요청 사이 1,200ms 대기만으로도 600건 장애 작업이 약 4시간 15분 걸릴 수 있다. DB 장애나 수집 lease 충돌에는 더 늦어질 수 있다. 가격의 마지막 성공 확인일과 실패 상태를 계속 확인해야 한다.

이 담당은 운영 환경 값을 변경하지 않았다. 통합 담당이 진행 중인 가격 갱신 종료 후 설정을 적용하고 새 예약 작업의 실제 제한 값·주기를 확인한다.

6회 갱신 후 남은 추가 두 상품도 같은 원인이었다. 원문을 내려받아 새 parser로 읽기만 확인했다.
