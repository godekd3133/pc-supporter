# Phase 0 — 견적 감사 서비스화 선행 검증

2차 전문가 회의 합의안(독립 견적 검증소 정체성)의 실행 전 검증 단계. 세 가지를 수행한다.

1. 실제 견적서 텍스트 → 카탈로그 부품 매칭 정밀도 오프라인 측정
2. 최소 이벤트 카운터(뷰/검사/생성/저장/공유)
3. 다나와 데이터 전략 결정

## 1. 매칭 정밀도 측정

### 방법

- 코퍼스: `scripts/fixtures/quote-samples.json` — 실제 샵다나와 견적 9건(구매 후기의 부품 표, ~75 라인) + 유입 포맷 커버용 합성 4건(커뮤니티 약식 나열, 완본체 스펙표, 수기식, 다나와 텍스트+가격). 총 117 라인, 부품 라인 83개.
- 실행: `npx tsx scripts/quote-match-precision.ts [--verbose]`
- 파이프라인: 라벨/가격/장식/유통사명 정규화 → 카테고리 추정 → 최소 `Part` 생성 → `quoteLineMappingCandidatesFor`(`shared/quote-audit.ts`, 커널 `catalogSeedMappingCandidatesFor` 위의 견적용 근사 매칭 어댑터) 매칭.
- 판정을 파싱/커버리지/매칭으로 분해: `coverage-gap`(제품이 카탈로그 어디에도 없음), `coverage-source`(카탈로그에는 있으나 danawa 소스 행만 없음), `match-miss`(있는데 매칭 실패), `wrong-*`(오매칭).

### 결과 (현재 카탈로그 169개 = seed 115 + danawa 54 기준)

| 판정 | 건수 | 비율 |
|---|---|---|
| 올바른 해결 | 15 | 18.1% |
| coverage-source (수집 확대로 해결) | 14 | 16.9% |
| coverage-gap (제품 자체 부재) | 33 | 39.8% |
| match-miss | 21 | 25.3% |
| wrong-high / wrong-review | **0 / 0** | 0% |
| skip 라인 처리 | 25/25 | 100% |
| unresolvable 라인 안전 처리 | 9/9 | 100% (false-high 0) |

### 해석

- **안전성은 합격**: 오매칭 0건, 모호 라인 거부율 100%. "모르면 남기는" 감사 철학에 정합.
- **병목은 매처가 아니라 커버리지**: 파싱·매칭 품질과 무관하게 해결 불가능한 라인이 57%(coverage-gap 40% + coverage-source 17%). 현재 수집 규모(`PAGES=1, LIMIT=5`)로는 견적 감사가 실전에서 대부분 "미확인"을 반환한다.
- **매처 약점 2건 확인** (match-miss 중 실제 결함):
  - 카탈로그 상품명의 유통사 접미사("…서린")가 nameExact를 깨고, 3자 모델 토큰("120")은 `starterModel.length >= 4` 규칙에 걸림 → 거의 동일한 상품도 0.12점으로 탈락. 견적 해결용 근사-이름 모드(접미사 무관 부분 일치 + 단축 모델 토큰) 필요.
  - SSD 라인에서 용량 토큰("1tb")이 제품 모델로 오선택되는 경향.
- **match-miss의 다수는 실은 올바른 거부**: "Crucial DDR5-5600" 라인을 "삼성 DDR5-5600"에 억지 매칭하지 않음 — 감사 맥락에서 정답. 해상도 지표로는 실패지만 제품 동작으로는 합격.

### 게이트 판정

**조건부 통과 — Phase 3 진입에는 두 선행 조건이 필요하다:**

1. 카탈로그 수집 규모 확대(아래 §3 데이터 전략 참조). 현 규모로는 해결율 ~18%가 상한이라 "검증소" 약속이 성립하지 않는다.
2. 견적 라인용 매처 확장(near-name 모드 + 유통사 접미사 정규화 + 카테고리별 모델 토큰 규칙). 커널 자체 재작성은 불필요하고, 견적 입력 경로에 얇은 어댑터로 충분할 것으로 보인다.

미달 시 후퇴선(의장 합의): "남의 견적 붙여넣기" 대신 "자동구성 결과 검증 + JSON/링크 불러오기"로 축소한다.

### 후속 — 선행조건 ② 매처 확장 (2026-09-17, `shared/quote-audit.ts`)

견적 입력 경로용 얇은 어댑터를 커널 위에 추가했다. 커널(`catalogSeedMappingCandidatesFor`, seed↔danawa 매핑 검수용)은 그대로 유지하고, 어댑터가 커널 결과를 우선 취한 뒤 부족분을 근사 매칭으로 채운다.

어댑터 동작:

- 유통사 접미사("서린", "제이씨현", "피씨디렉트" 등 19개)를 견적 라인과 카탈로그 상품명 양쪽에서 제거한 뒤 compact 비교. 완전 일치(`compactEqual`)만 high 허용(커널 name_exact 가중치와 동일).
- 근사 모델 매칭: 모델 토큰의 compact 포함 관계를 보되, needle이 숫자로 끝나고 바로 뒤에 `ti|super|xt|xtx|k|f|g|e|a|x|ks`가 붙으면 다른 SKU로 거부("5060"→"5060Ti" 방지).
- 앵커 요구: 근사 모델 매칭은 비스펙·숫자없는 이름 토큰(브랜드·라인) 공유를 요구해 spec만 같은 다른 제품(DDR5-6000 → 타사 DDR5-6000)이 붙지 않게 한다. 차별화 카테고리(cpu/motherboard/gpu/case/cooler/psu)는 비브랜드 앵커를 요구해 "MSI MAG B760M 박격포"가 "MSI PRO B760M-A"로 붙는 것을 막고, 규격품(memory/ssd/hdd)은 브랜드 앵커만으로 허용한다("삼성 DDR5-5600"→"삼성전자 DDR5-5600").
- 세대 토큰 충돌 거부: `wifi7`≠`wifi6e`, `d6`≠`d7`, `ddr4`≠`ddr5` 등 양쪽에 있는 버전 토큰이 다르면 매칭하지 않는다.
- 용량 토큰 불일치 감점: 같은 제품군의 다른 용량 변형(2TB→1TB)은 review 수준으로만 표시.
- 카테고리별 모델 추출 개선: ssd/hdd는 용량·인터페이스 토큰을 제외한 알파뉴메릭 모델("P3","G4","C910G")을 선택하고, 메인보드는 칩셋+변형 문자를 붙여 잡는다("B650M-K"→b650mk). 한국어 변형 표기(슈퍼→super, 울트라→ultra)를 정규화 계층에서 통일.
- 근사 매칭 confidence는 review 한정 — unresolvable 라인의 false-high는 유지된 0.

재측정(같은 코퍼스 117라인, 카탈로그 171개 = seed 115 + danawa 56):

| 판정 | 전 | 후 |
|---|---|---|
| 올바른 해결 | 15~16 (18.1~19.3%) | 24 (28.9%) |
| coverage-source | 14 | 16 |
| coverage-gap | 33 | 33 |
| match-miss | 21 | 10 (전부 제품 부재의 정직한 거부) |
| wrong-high / wrong-review | 0 / 0 | **0 / 0** |
| unresolvable false-high | 0 | 0 |
| 실측 샘플 해결율(real only) | 19.7% | 27.3% |

해석: 매처 확장으로 해결율은 ~2배 가까이 올랐으나 절대 한계는 그대로다 — coverage-gap 33 + coverage-source 16 = 59%가 카탈로그 부재로 여전히 "미확인"이 된다. 선행조건 ①(수집 규모 확대) 없이는 "검증소" 약속이 성립하지 않는 판정은 변함없다. 남은 match-miss 10건은 Crucial DDR5-5600 CL46, KLEVV DDR5-6000 라인, SuperFlower SF-850F14GE, GIGABYTE B850 AORUS ELITE WIFI7, B760 박격포처럼 실제로 카탈로그에 없는 제품이다.

## 2. 최소 이벤트 카운터

- `server/usage-events.ts`: 익명 일별 카운터(`data/usage-events.json`, 90일 유지, 직렬화 파일 쓰기). PostgreSQL 모드에서도 동일 파일 사용 — 분석용이 아닌 측정용이라 손실 감수.
- 서버 계수(성공 응답 시): `check`=/api/compatibility/check, `recommend`=/api/builds/recommend, `save`=/api/builds, `share`=/api/{comparisons,version-comparisons,budget-ladders,watchlists} 생성.
- 클라이언트 비컨: `app_open`만 `POST /api/events`(204). 서버 계수 이벤트는 endpoint가 400으로 거부해 이중 계수 차단.
- 조회: `GET /api/admin/usage-events`(admin 전용) → 일별/누계.
- 테스트: `server/usage-events.test.ts` — 화이트리스트 거부와 직렬화 동시 증가 검증.

## 3. 다나와 데이터 전략 (결정)

### 리스크 구조

- **법**: 대법원 2021도1533은 크롤링 *형사*책임 부정이었으나, 민사 DB권 침해는 별건에서 인정 사례 존재. 다나와 2025.7 판매점 약관에 API/MCP 조항 신설 — 사업화·외부 노출 시 전문가 검토 선결.
- **차단**: 수집 규모를 키우면 차단 리스크가 커진다.
- **단일 소스**: 다나와 장애·정책 변경이 곧 서비스 중단.

### 결정

1. **수집 규모를 단계적으로 올린다.** 견적 감사 해결율이 다나와 행 수에 정비례하므로 `PAGES`/`LIMIT`을 상향하되, (a) 일일 수집량이 다나와 DB의 "상당한 부분"에 해당하지 않는 수준 유지, (b) User-Agent/요청 간격 등 정중한 수집 유지, (c) 차단·약관 변경 감지를 crawl manifest 오류로 관찰.
2. **모든 가격 표현에 "다나와 기준" 출처를 명시한다.** 가격은 감사의 "관찰 근거"이지 판정이 아니며, 이미 UI/계약이 근거 표시 중심이라 부합.
3. **중기 이중화 옵션을 문서화한다.** 컴퓨존/가격비교 대안 소스, 수동 seed 확충 경로(`import:private-catalog` 이미 존재). 견적 감사 기능이 수익화되기 전에 법 검토 + 소스 이중화를 선행한다.
4. **MCP/외부 API 노출은 보류.** 공개 REST는 이미 존재하나, 다나와가 MCP를 약관에 명시하기 시작한 시점의 역방향 노출은 법적 신경전을 유발할 수 있다.
