# PC Supporter

[![CI](https://github.com/godekd3133/pc-supporter/actions/workflows/ci.yml/badge.svg)](https://github.com/godekd3133/pc-supporter/actions/workflows/ci.yml)

현재 구현을 의존성 순서와 검증 근거별로 분류한 문서는 [`docs/development-process.md`](docs/development-process.md)에서 확인할 수 있습니다. 공개 저장소에는 코드와 결정적 seed 데이터만 포함하고, 다나와 수집 원본·사용자 저장 상태·로컬 실행 산출물은 [`data/README.md`](data/README.md)의 정책에 따라 제외합니다.

다나와 부품 카탈로그와 설명 가능한 규칙 엔진으로 PC 견적 호환성을 검사하는 웹서비스입니다.

홈의 `DATA TRUST` 패널은 현재 실제 메타데이터를 사용해 핵심·주변 부품 수, 가격 확인률, 스펙 일부 부족 수, CPU Cinebench·GPU 3DMark 완전 점수 세트 커버리지, 카탈로그 갱신 시점과 엔진 버전을 표시합니다. 가격 확인률과 성능 근거 커버리지는 미확인 상품·미완전 점수 세트를 반올림으로 숨기지 않도록 소수 첫째 자리까지 보여주며, 이는 성능 순위가 아니라 추천 근거의 범위를 나타냅니다. 메타데이터 동기화 중·일부 실패·갱신 시점 확인 필요 상태도 검사 준비 상태와 분리합니다.

이 브라우저에 저장된 초안이나 마지막 검사 결과가 있으면 홈에 `CONTINUE BUILD` 카드가 나타납니다. 선택한 핵심 범주·주변 부품 수와 마지막 검사 위험 카운트를 확인한 뒤 견적 편집기 또는 최신 결과로 복귀할 수 있으며, 입력 fingerprint가 달라진 결과는 `재검사 필요`로만 안내해 오래된 결과를 최신 결과처럼 열지 않습니다.

실측 추세 비교는 전체 회차와 동일 부하 조건을 분리하고, 조건이 같은 회차 사이에서만 직전 대비 변화량을 계산합니다. 주변 온도 보정값을 별도로 보여주며, 동일 조건에서 온도·팬 RPM·체감 소음이 2회 연속 상승할 때는 절대 안전·위험 판정이 아닌 `재확인 신호`로 안내합니다.

HWiNFO·OCCT 센서 CSV는 열 이름을 자동 매핑한 뒤 적용 전 미리보기를 거치며, 온도·팬 RPM 대표값과 함께 최대 240개로 압축한 시간축 시계열을 현재 회차에 보존합니다. 화면에서는 CPU·GPU 온도 선형 추세와 최저·평균·최고 요약을 보여주고, 서버 공유 snapshot에는 시계열 포인트 수만 포함해 원본 파일과 compact 저장을 분리합니다.

CPU·GPU 사용률·클럭·소비전력 열도 선택적으로 시계열에 포함하며, 미리보기에서 추가 센서 매핑을 확인할 수 있습니다. 이 값들은 온도 변화의 부하 맥락과 리포트 근거를 보강하지만, 전력 한도나 안정성의 자동 승인·차단 판정에는 사용하지 않습니다.

사용률 시계열이 있으면 한 번의 테스트를 유휴·CPU 부하·GPU 부하·혼합 부하·부분 부하 구간으로 연속 분할하고, 구간별 사용률·온도·소비전력과 온도 변화/100W 관찰값을 계산합니다. 유휴 ≤20%, 고부하 ≥70%, 반대 센서 ≤40%라는 분류 기준과 사용률 커버리지·미분류 포인트를 함께 보여주며, 사용률이 없으면 구간을 추정하지 않습니다.

각 부하 구간은 후반 최소 3개 온도 샘플의 범위가 2°C 이내인지 확인해 CPU/GPU별 안정화 관찰과 안정화 시점을 표시합니다. 샘플 수나 시간축이 부족하면 안정화를 확정하지 않고 `샘플 부족`·`안정화 미확인`으로 남깁니다.

활성 회차에는 같은 부하 도구·시나리오·테스트 시간의 직전 회차를 구간 종류와 발생 순서로 매칭해 종료 온도·평균 사용률·평균 소비전력·온도 변화/100W·안정화 상태의 변화를 별도로 보여줍니다. 조건이 달라지거나 이전 회차가 없으면 비교하지 않고 그 이유를 표시합니다.

같은 조건의 2개 이상 회차에 시계열이 있으면 각 회차의 샘플을 0~100% 테스트 진행률로 정규화한 CPU/GPU 온도 overlay를 제공해, 조립 직후·드라이버 설치 후·장시간 부하 후의 전체 추세를 한 화면에서 비교합니다. 회차별 원본 포인트 수와 최고 온도·평균 사용률을 함께 표시하며, 조건이 다르거나 시계열이 부족한 회차는 overlay에서 제외합니다.

overlay는 기준 회차를 바꾸고 포함할 회차를 체크박스로 선택할 수 있으며, 선택된 회차 수를 리포트의 overlay 요약에도 반영합니다. 기준 회차의 부하 조건과 다른 회차는 후보에서 제거해 비교 오해를 줄입니다.

선택된 회차에는 CPU·GPU 최고 온도 낮은 순, 안정화 확인 우선·확인 시점 순, CPU·GPU 평균 소비전력 관찰 순의 비교 요약을 제공합니다. 각 행에는 첫 선택 회차 대비 변화량을 표시하며, 전력 순위는 성능 우열이 아니라 관찰 순이고 안정화 샘플이 부족하면 순위를 부여하지 않습니다.

실측 결정 요약은 선택 회차가 2개 이상일 때 기준 회차와 최신 선택 회차의 열 상태·안정화 상태를 `개선 관찰`·`변화 없음`·`재확인 필요`·`비교 불충분`으로 분리합니다. 온도 상승이나 최신 안정화 미확인은 재확인으로 안내하지만, CPU/GPU 전력 변화는 전체 상태를 악화·개선으로 승격하지 않고 `관찰상 낮음/높음`으로만 기록합니다.

실측 리포트는 현재 비교 필터 기준의 회차·조건·원본/주변 온도 보정값·델타·측정 출처·재확인 신호를 Markdown·CSV·요약 JSON으로 내보내며, 시계열의 시작→종료 관찰 추세·변화율·최고점 시점·마지막 구간 범위도 함께 기록합니다. 원본 CSV 파일과 시계열 원시 행은 리포트에 포함하지 않습니다.

CSV 적용 후에는 입력 품질 카드에서 유효/전체 행, 기본 센서 5종 완성도, 추가 부하 센서 수, 시간축 유무, 압축 시계열 포인트 수, 제외 행과 잘못된 셀 수를 확인할 수 있습니다. 이 상태는 측정 비교의 근거 범위를 설명할 뿐 호환성·안전·고장 판정이 아닙니다.

시간축이 있는 CSV는 정상 샘플 간격의 중앙값을 기준으로 timestamp 공백·역순을 검사합니다. 비정상적으로 긴 간격은 `공백 있음`과 최대 공백·예상 누락 샘플로 표시하고, 유효 timestamp가 부족하면 `확인 불가`로 남겨 시계열을 조용히 이어 붙이지 않습니다.

공백·역순 경계는 입력 품질 경고에만 머물지 않고 실제 CPU/GPU 부하 구간과 온도 차트의 독립 구간으로 분리합니다. 공백 전후의 같은 부하 라벨도 하나의 연속 구간으로 합치지 않습니다.

측정 품질이 `확인 필요`이거나 시간축이 `공백 있음`인 회차는 같은 조건이어도 정상 델타·재확인 상승 신호·다회차 overlay에서 제외합니다. 대신 추세 표에는 `측정 품질 확인`, 품질 재확인 신호와 제외 사유를 표시해 끊긴 데이터를 정상 회차로 오해하지 않게 합니다.

홈 화면에는 오류 수정 흐름을 보여주는 `오류 시연 견적`과, 호환 완료 후 업그레이드·조합·구매 체크 흐름을 보여주는 `호환 완료 시연 견적`을 분리해 제공합니다. 두 시연 구성은 모두 현재 카탈로그의 실제 부품 ID를 사용하며, 사용자가 임의 선택을 시작하기 전에 서비스의 양쪽 결과 경계를 재현할 수 있습니다.

결과 화면의 대체 후보는 빠른 범위 추천과 사용자가 직접 실행하는 `전체 후보 정밀 탐색`을 분리합니다. 정밀 탐색은 현재 구성에 후보를 실제로 대입해 안전·확인 필요·차단 위험을 모두 분류하며, 차단 후보는 이유를 보여주되 자동 적용하지 않습니다. 하나의 finding에서 GPU·PSU처럼 교체 대상 범주가 둘 이상이면 한 범주의 후보만 독점하지 않도록 대상 범주별 대표 후보를 먼저 보장하고, 후보 카드에 실제 교체 범주를 표시합니다.

후보 비교표에서는 선택한 안전·확인 필요 후보를 `가상 적용`해 전체 finding·위험 카운트·가격 변화를 비파괴적으로 확인할 수 있습니다. 가상 결과에서 실제 적용을 선택해도 먼저 변경 미리보기를 거치며, 차단 후보는 가상 적용과 실제 적용을 모두 막습니다.

정밀 후보 선택기에서는 위험도(`안전`·`확인 필요`·`차단`)를 별도로 필터링할 수 있습니다. 후보별 전체 평가 결과는 견적·카탈로그 revision·finding·검색·정렬·스펙 조건을 포함한 cache key로 2분간 재사용하고, 위험도·성능·추천 근거·예산 필터 변경은 재평가 없이 적용합니다. GPU·케이스·PSU 정밀 후보에는 대체 후보 자체의 물리 구매 근거도 함께 전달하며, 호환 규칙은 통과해도 물리 출처가 없으면 `호환 확인 · 물리 확인 필요`로 분리 표시합니다. 이 범주의 선택기에서는 `물리 근거 확인됨`·`물리 근거 확인 필요` 필터를 추가로 사용해 서버가 계산한 근거 상태만 남길 수 있고, 필터로 제외된 후보 수와 조건 완화 안내를 함께 표시합니다.

편집기의 `검사 전 사전 점검`은 호환성 판정과 분리된 입력 준비 단계입니다. 필수 CPU·쿨러·메인보드·RAM·케이스·파워 선택 여부를 계산하고, 내장 그래픽을 끈 경우 외장 GPU 선택도 요구합니다. 선택한 부품·주변 부품의 카탈로그 상세 누락, 카탈로그에서 찾지 못한 ID, 가격 미확인을 별도로 표시하지만 검사를 막지는 않으며, 실제 소켓·전력·장착·슬롯 호환성은 검사 버튼의 규칙 엔진 결과만 기준으로 판단합니다.

사전 점검에서 다나와 원문이 등록된 선택 부품의 스펙 누락·가격 미확인을 발견하면 해당 항목에 `원문 다시 확인`을 제공합니다. 단건 `원문 다시 확인`과 `확인 대상 n개 모두 확인`을 제공하며, 일괄 확인은 최대 12개를 순차 처리하고 마지막에 현재 구성만 한 번 재검사합니다. 단건 재확인은 기존 제한·cooldown·원문 검증·재검사 흐름을 사용하고, 수동·seed·원문 미등록 데이터에는 확인되지 않은 주소로 요청하지 않습니다.

편집기의 `견적 JSON 저장`은 현재 부품 선택·수량·주변 부품·M.2 슬롯 배치·추천 기준을 schemaVersion이 포함된 파일로 내보냅니다. `견적 JSON 가져오기`는 envelope와 raw selection legacy 형식을 검증하고, 잘못된 버전·수량·슬롯·추천 기준이 하나라도 있으면 현재 견적을 바꾸지 않습니다. 정상 가져오기 후에는 카탈로그에 없는 부품을 임의로 제거하지 않고 사전 점검에 다시 표시하며, 선택 상세를 동기화한 뒤 사용자가 호환성 검사를 새로 실행하도록 합니다.

견적 JSON을 읽으면 바로 현재 입력을 바꾸지 않고 `견적 JSON 미리보기`에서 먼저 사전 점검 결과와 선택 카테고리·부품·주변 부품·M.2 배치·추천 기준을 확인합니다. 사용자가 명시적으로 `이 구성으로 가져오기`를 눌러야 현재 편집기를 교체하며, 가져온 뒤 호환성 검사는 자동 실행하지 않습니다.

미리보기에는 현재 편집기와 가져올 파일의 차이를 `변경 전 → 변경 후`로 표시합니다. 부품 순서만 바뀐 반복 선택은 변경으로 세지 않으며, 부품 교체·수량·주변 부품·M.2 배치·내장 그래픽·추천 기준 변화를 항목별로 확인할 수 있습니다.

결과 화면의 `구매 전 실행 체크리스트`도 JSON으로 저장·가져올 수 있습니다. 가져오기는 현재 체크 상태를 즉시 덮어쓰지 않고 내보낸 시각·파일 항목 수·현재 완료/가져올 완료·새로 체크·해제·유지 항목을 먼저 보여줍니다. 사용자가 `이 상태로 가져오기`를 눌러야 적용되며, 미리보기 중 검사 결과로 체크리스트 항목 구성이 바뀌면 오래된 상태를 적용하지 않고 다시 가져오도록 막습니다. 현재 견적에 없는 체크 항목은 무시 수로 분리하고, 다른 견적·잘못된 버전·잘못된 JSON은 현재 상태를 바꾸지 않습니다.

결과 화면에는 `구매·조립 실행 순서`를 별도 요약으로 표시합니다. 호환성 차단·근거 확인·구매·메인보드 사전 조립·케이블/주변 부품 연결·POST/BIOS/온도 테스트의 6단계를 현재 결과 상태와 선행 단계에 따라 `구매 보류`·`확인 필요`·`앞 단계 대기`·`진행 가능`으로 나눕니다. 각 단계에서 관련 수리 플랜·데이터 신뢰도·구매 목록·주변 부품·체크리스트로 이동할 수 있으며, 결과 텍스트 리포트와 JSON 리포트에도 같은 순서와 상태를 보존합니다.

HWiNFO·OCCT 계열 센서 CSV는 지원 헤더를 자동 매핑해 온도·팬 RPM은 유효 행의 최대값, 주변 온도는 평균값으로 집계하고, 인식 열·유효 샘플·제외 행을 미리 보여준 뒤 현재 회차에 적용합니다. 사용자는 부품을 검색해 견적을 구성하고, CPU·메인보드 소켓, RAM 세대·DIMM/SO-DIMM 물리 규격·용량·슬롯, M.2 슬롯·NVMe/SATA 연결 방식·PCIe 세대·PCIe 레인 공유 확인 필요, SATA 포트, PCIe 그래픽카드 장착 슬롯, 케이스 장착 공간, 케이스 팬과 메인보드 팬/RGB 헤더·5V ARGB·12V RGB 전압 연결 여유, GPU 전력·PCIe 보조전원·길이·두께 간섭, PSU 깊이·케이스 허용 길이·폼팩터, CPU 쿨러, 파워서플라이 정보를 한 번에 검사할 수 있습니다. 결과는 차단 오류·주의·확인 필요로 나뉘며, 오류 카드에서 대체 부품을 적용하고 재검사할 수 있습니다. M.2 NVMe SSD가 메인보드보다 높은 PCIe 세대를 요구하면 물리적 불호환으로 단정하지 않고 실제로는 낮은 세대로 링크될 수 있는 성능 주의와 호환 세대 대안을 함께 보여줍니다. 각 오류 카드에서는 판정 규칙·비교 기준·데이터 경계를 펼쳐 확인할 수 있고, 대체 후보를 2~3개 선택해 가격·유사도·유통 조건·핵심 스펙을 한 표에서 비교할 수 있습니다. 결과 화면에는 부품 간 호환 관계 맵도 표시해 어떤 연결에서 문제가 발생했는지 보여줍니다. 여러 오류가 겹치면 최대 3개 부품을 함께 바꾸는 해결 플랜을 호환성 감소량·유사도·가격 변화와 함께 제안합니다. 검사 결과에는 현재 카탈로그 스펙을 기준으로 한 상대 성능 지수, 자원 여유와 확장성 병목, 다음 행동 우선순위, 선택 부품별 갱신 시점·스펙 완성도·가격 확인 상태도 함께 표시합니다. 현재 구성에 맞는 주변 부품 보완 후보도 표시하며, 추천 카드에서 주변 부품을 견적에 추가하면 수량·가격이 선택 목록에 반영되고 호환성 재검사·저장·공유에도 함께 포함됩니다. 빈 견적에서는 사용 목적과 예산으로 호환 가능한 자동 초안도 만들 수 있고, 핵심 부품과 분리된 주변 부품 카탈로그도 탐색할 수 있습니다.

GPU가 선택되면 결과 화면의 `GPU 실장·전원 요약`에서 GPU 길이와 케이스 허용 길이의 실제 여유, 두께 경고 기준, GPU 소비전력·권장 PSU·선택 PSU의 전력 여유, GPU 보조전원 선택지와 PSU에서 확인된 커넥터를 하나의 증거 묶음으로 확인합니다. GPU 원문에 실제로 적힌 `2x8핀 to 16핀` 구성품만 별도 어댑터 경로로 표시하고, 변경 이력에만 남은 과거 경로는 현재 연결 선택지로 사용하지 않습니다. PSU 원문에 확인되는 풀모듈러·세미모듈러·케이블 일체형과 12V 싱글·다중레일 표기는 보조 설명으로 표시하지만, 커넥터 수량만으로 독립 케이블·레일 구성이나 케이블 굽힘 반경을 추정하지 않습니다. 케이스 원문에서 확인되는 `120mm/280mm 수랭쿨러 제공` 같은 안정 영역의 라디에이터 크기와 전면·상단 등 위치 정보도 분리해 정규화하며, 케이스와 쿨러 양쪽 위치가 확인된 경우에만 위치까지 대조합니다. 위치가 없거나 `[변경사항]`에만 있는 과거 표기는 확인 필요로 남기고 현재 판정에 사용하지 않습니다. 물리 검수 근거가 등록되지 않은 GPU·케이스·다중 8핀 PSU는 길이·전력·커넥터 수량이 통과해도 `GPU 실장·전원 요약`과 `구매 준비도`에서 확인 후 구매로 표시하며, 실제 물리 충돌로 단정하지 않습니다. 등록된 검수값은 출처 메모와 HTTPS 원문 링크를 함께 결과·대체 후보·공유 비교표에 전달하고, 숫자만 있고 출처가 없는 물리값은 `확인 필요`로 낮춰 근거 없는 `확인됨` 표시를 막습니다. 케이스 전면 라디에이터·팬·측면 패널 간섭과 실제 배선은 제조사 원문과 조립 조건을 별도로 확인하며, 같은 구조화 결과는 텍스트 리포트에도 포함됩니다.

관리자 데이터 센터의 `GPU·케이스·PSU 물리 호환 검수`에서는 판매 목록만으로 확정하기 어려운 GPU 물리 슬롯 점유, GPU 전원 케이블 굽힘 최소 여유, 케이스 측면 케이블 여유, PSU의 독립 PCIe 케이블 런 수와 분배 구조를 제조사 매뉴얼 근거와 함께 override로 등록할 수 있습니다. override에는 제조사 모델/SKU를 필수로, 문서 revision을 선택으로 기록해 같은 시리즈의 다른 변형 문서를 잘못 연결하는 위험을 줄입니다. override는 원본 카탈로그 파일을 덮어쓰지 않고 별도 저장소에 보관하며, 런타임 GPU FIT에는 수치와 출처 메타데이터를 함께 전달하고 저장 전에는 원본 카탈로그에서 제거합니다. 현재 데이터에는 공식 ZOTAC 브로셔와 Palit 공식 사양에서 `3.5 slot`이 명시된 RTX 5090 SOLID OC·SOLID OC White·AMP Extreme INFINITY·GameRock·GameRock OC 5건의 GPU 슬롯 점유값이 부분 검수로 등록되어 있습니다. 케이블 굽힘 여유·케이스 측면 여유·PSU 독립 런 수는 아직 입력하지 않았으므로 완료 coverage나 구매 준비 완료로 승격되지 않습니다. 호환 오류와 확인 필요가 없는 구성에서는 선택된 CPU·GPU·RAM·SSD·HDD·쿨러·PSU·케이스·메인보드에 대해 호환성을 유지하는 업그레이드 후보를 별도로 제안합니다. 후보 교체 후 새 차단 오류·확인 필요·주의가 생기면 제외하고, 비교 가능한 카탈로그 스펙이 실제로 개선된 경우에만 비교 변화율·향상 지표·유사도·가격 차이·적용 후 재검사 버튼을 표시합니다. 업그레이드 후보는 현재 선택이 하나인 핵심 부품을 대상으로 CPU·GPU·RAM·SSD·HDD·CPU 쿨러·PSU·케이스·메인보드의 성능·용량·냉각·전력·확장성 변화를 비교할 수 있습니다. 다중 RAM·SSD·HDD 구성은 한 항목만 임의로 교체하지 않습니다. HDD는 일반 SATA 인터페이스가 확정된 경우만 SATA 메인보드 직접 연결 후보로 인정하고, SAS 등 별도 컨트롤러가 필요한 인터페이스나 원문 미확인 후보는 차단·확인 필요로 분리합니다.

결과 분석에는 CPU와 GPU의 카탈로그 상대 지수를 비교한 밸런스 신호도 표시합니다. 두 점수 차이가 작으면 균형 범위, CPU가 크게 낮으면 CPU 병목 가능성, GPU가 크게 낮으면 GPU 병목 가능성으로 안내하고 먼저 비교할 업그레이드 방향을 제안합니다. 이는 실제 FPS나 병목을 확정하는 측정값이 아니라 선택한 사용 목적·해상도 가중치로 계산한 상대 지수이며, 필요한 CPU·GPU 스펙이 부족하면 밸런스를 추정하지 않습니다.

추천 응답은 한 카테고리만 과도하게 채우지 않도록 카테고리별 최대 2개, 전체 최대 8개로 균형을 맞추며, 화면에서는 그중 최대 3개를 비교할 수 있습니다.

추천 보드에서는 전체·CPU·GPU·RAM·SSD·HDD·쿨러·PSU·케이스·메인보드 필터를 후보 수와 함께 제공하며, 특정 카테고리만 빠르게 좁힐 수 있습니다. 후보 카드의 상세 스펙을 펼치면 정규화된 비교 항목, 저장된 원문 스펙, 데이터 품질, 누락 필드, 갱신일, 유통 조건과 허용된 다나와 원문 링크를 확인할 수 있습니다. 원문 링크는 등록된 허용 호스트만 화면에 노출하며, 후보 추천 근거와 구매 전 확인 경계를 분리합니다.

부품 선택기의 `호환 핵심 조건`은 일반 카탈로그와 문제 해결 후보 탐색에 같은 방식으로 적용됩니다. CPU·쿨러·메인보드는 소켓, CPU·메인보드·RAM은 메모리 세대, 케이스·메인보드·RAM·SSD·PSU는 폼팩터, 메인보드는 RAM 슬롯·M.2 슬롯·SATA 포트, 케이스는 GPU 허용 길이·쿨러 허용 높이·HDD 베이·PSU 허용 길이, GPU는 최대 길이, 쿨러는 최소 냉각 용량, PSU는 최대 깊이를 직접 입력할 수 있습니다. 현재 견적에서 확인된 값만 `현재 구성 기준 적용`으로 자동 채울 수 있으며, 값이 등록되지 않은 부품은 조건을 충족한다고 추정하지 않고 결과에서 제외합니다. 서버가 스펙 조건으로 제외한 수와 자동 조건에 사용하지 않은 정보도 화면에 함께 표시합니다. 조건별 제외 근거는 정보 누락과 실제 조건 미달을 나눠 보여주며, 여러 조건에 동시에 걸린 부품을 단순 합산하지 않습니다.

부품 선택기는 편집기의 `추천 기준`에 설정된 구매 조건을 기본값으로 이어받습니다. 예를 들어 편집기에서 `벌크 포함`을 선택했다면 선택기 역시 해당 조건으로 시작하며, 선택기 안에서 사용자가 직접 바꾼 구매 조건은 현재 탐색 중에 그대로 유지됩니다.

게이밍 프로필에서는 FHD(1080p)·QHD(1440p)·4K(2160p) 목표 해상도와 60Hz·144Hz·240Hz 목표 주사율을 선택할 수 있습니다. 해상도별 보수적인 권장 VRAM 기준(8GB·12GB·16GB)을 사용해 GPU의 VRAM·메모리 대역폭·스트림 프로세서 가중치를 조정하고, 목표 주사율은 CPU 싱글 성능·GPU 처리 성능 비교 가중치에 반영합니다. 결과 분석·업그레이드·자동 구성·대체 후보 비교·견적 JSON·히스토리 fingerprint에도 같은 기준을 전달합니다. 이 기준은 게임·옵션·업스케일러별 실제 FPS나 프레임타임을 보장하는 벤치마크가 아니며, VRAM이 확인되지 않으면 추정하지 않고 확인 필요로 남깁니다. 자동 구성도 같은 해상도·주사율 기준으로 후보를 정렬하지만 전력·장착 공간·PCIe·보조전원은 기존 호환성 규칙으로 별도 검증합니다.

결과 분석에는 CPU·GPU의 카탈로그 상대 지수를 비교한 밸런스 신호를 표시합니다. 두 점수 차이가 20점 미만이면 균형 범위, GPU가 크게 높으면 CPU 병목 가능성, CPU가 크게 높으면 GPU 병목 가능성으로 안내하고 먼저 비교할 업그레이드 방향을 제안합니다. 선택한 해상도의 GPU VRAM이 권장 기준보다 낮으면 호환성 차단과 분리된 성능 주의 신호로, VRAM 원문이 없으면 확인 필요 신호로 다음 행동에 올립니다. 이는 실제 FPS·프레임타임·게임별 병목을 확정하는 측정값이 아니며, CPU·GPU 비교 데이터가 부족하면 밸런스를 추정하지 않습니다.

분석 결과에는 선택한 사용 목적의 상대 지수를 해석한 `현재 구성의 강점`과 `먼저 볼 영역`도 표시합니다. 75점 이상인 카테고리는 강점 후보로, 60점 미만인 카테고리는 보완 후보로 최대 2개씩 보여주며, 해당 기준은 카탈로그 구성에 따라 달라집니다. 실제 절대 성능이나 모든 작업의 체감 순위를 의미하지 않습니다.

호환 유지 업그레이드 후보는 선택된 CPU·GPU·RAM·SSD·HDD·쿨러·PSU·케이스·메인보드 중 단일 구성만 안전하게 교체할 수 있을 때 후보로 제안합니다. 다중 RAM·SSD·HDD 선택은 임의로 하나만 바꾸지 않고 기존 문제 해결 플랜을 사용합니다. 후보는 최대 3개까지 선택해 현재 부품과 함께 비교할 수 있으며, 비교표에는 개선 지표·상대 변화율·현재 가격과 후보 가격·가격 변화·유사도뿐 아니라 후보를 전체 규칙 엔진에 대입한 뒤 부품 종류에 맞는 전력·냉각·장착·메모리·M.2·SATA·HDD 베이 여유와 전체 확장성 점수 변화를 표시합니다. 후보 카드의 `확장성 개선 폭` 정렬은 후보 적용 전후의 정규화 확장성 점수 차이를 사용하며, 양수·음수·근거 부족을 구분해 보여줍니다. 모든 후보는 새 차단 오류·확인 필요·주의가 늘지 않는 경우에만 노출되며, 비교표의 호환 여유는 실제 조립 환경을 대신하지 않습니다.

추천 기준에 목표 예산을 입력하면 업그레이드 후보마다 핵심 부품 합계의 현재값·교체 후 값·목표 예산 대비 여유 또는 초과 금액을 함께 표시합니다. 가격이 하나라도 확인되지 않으면 예산 적합 여부를 확정하지 않고 `핵심 금액 확인 필요`로 남기며, 가성비 우선 정렬에서는 예산 내 후보를 먼저 보되 예산 밖 후보도 숨기지 않습니다. 주변 부품 금액은 이 비교의 핵심 부품 합계와 분리해 과도한 확정 표현을 피합니다. 업그레이드 확장 대상은 카테고리별 성능·용량·확장성 지표를 함께 비교하고, 새 호환 위험을 전체 규칙 엔진으로 재검증합니다.

단일 후보 외에도 서로 다른 두 카테고리의 업그레이드를 조합해 가능한 안전 조합을 모두 재평가하고, 안전한 2개·3개 부품 조합 중 최대 3개를 화면에 표시합니다. 조합 전용 후보 풀은 카테고리별 최대 4개·전체 24개로 확장하며, 먼저 안전한 2개 조합을 만들고 그중 기준별 beam 상위 24개만 3개 조합으로 확장해 응답 시간을 통제합니다. 후보 쌍·3개 조합을 제한적으로 재검사해 화면용 단일 후보 목록에 없던 조합도 찾습니다. 조합 전체를 다시 평가해 새 차단 오류·확인 필요·주의가 생기면 제외하고, 조합별 변화 합산·카테고리별 교체 내역·수량을 표시합니다. 현재 탐색 후보 수·2개/3개별 검증 조합 수·안전 조합 수와 화면에 표시하는 상위 3개를 구분하며, 조합 전체의 적용 전후 확장성 점수와 지표 완성도도 계산합니다. 조합 정렬에서 확장성 개선 폭을 선택할 수 있고, 목표 예산을 입력하면 조합을 적용한 뒤의 핵심 합계와 예산 내·초과 상태도 계산합니다. 조합 적용은 기존 전체 재검사 흐름을 사용합니다.

업그레이드 조합도 바로 적용하지 않고 `가상 적용`으로 조합 전체를 현재 견적에 대입할 수 있습니다. 조합별 교체 부품·수량·가격 변화, 적용 전후 호환 상태·위험 카운트·총액·확장성 여유 변화, 적용 후 남는 finding을 확인한 뒤 실제 변경 미리보기로 이동하며, 가상 결과에서 위험이 증가한 조합은 적용을 막습니다. 현재 조건에서 조합 후보가 생성되지 않으면 해당 패널 자체를 숨기고 단일 업그레이드·수리 플랜 흐름만 표시합니다.

호환성 API의 2개·3개 조합 응답은 `upgradeBundlePayload`로 정규화합니다. 고유 업그레이드 후보는 한 번만 전달하고 각 조합은 카테고리·부품 ID 참조로 전달해 반복 상세 데이터를 제거하며, 클라이언트가 기존 조합 객체로 복원합니다. 후보의 이름·가격·이미지는 먼저 전달하고 전체 Part 스펙·저장 원문은 조합 카드의 `상세 스펙 보기`를 눌렀을 때만 `/api/parts/:id`에서 지연 조회합니다. 처음 표시되는 조합의 미완료 후보 ID는 같은 `catalogSnapshotAt` 범위에서 `/api/parts/batch`로 한 번에 prefetch하고, 후보 ID별 in-flight·완료 캐시를 공유해 여러 카드의 중복 요청을 막습니다. 카탈로그 기준이 바뀌면 캐시 namespace도 바뀌며, 실패한 조회는 캐시하지 않아 재시도할 수 있습니다. payload 버전이 없거나 참조가 손상된 구버전·오류 응답은 기존 full bundle 배열 fallback을 사용하거나 안전하게 표시하지 않습니다.

부품 단건과 GET batch 조회에는 응답 본문 기반 `ETag`와 `private, max-age=0, must-revalidate`를 적용합니다. 같은 부품·ID 목록을 다시 요청하면 `If-None-Match` 조건부 요청에서 304를 반환하고, 응답 내용이나 카탈로그 기준이 바뀌면 새로운 ETag를 발급합니다. 기존 POST batch API는 호환성을 위해 유지하며, 조합 prefetch는 HTTP 캐시가 가능한 GET batch 경로를 사용합니다. 호환성 결과 cache도 compact 결과와 직렬화된 응답 본문을 함께 보관해 cache HIT에서 같은 JSON을 다시 직렬화하지 않습니다.

견적에 추가한 주변 부품은 가격 합계뿐 아니라 규격이 확정 가능한 범위에서 본체와 별도 호환 점검을 실행합니다. M.2 방열판은 선택 SSD 길이 규격, 쿨링팬은 케이스 장착 팬 크기, 팬 허브는 케이스 기본 팬 수와 분배 포트 수, UPS는 확인된 CPU·GPU 전력과 출력(W), M.2 변환 어댑터는 선택 SSD의 폼팩터·NVMe/SATA 신호 지원을 비교하며, 불일치·여유 부족은 차단·주의·확인 필요로 표시합니다. 팬 헤더가 실제로 부족하면 외부 전원과 분배 포트가 확인된 팬 허브를, RGB 전압·출력 여유가 부족하면 케이스 전압·출력 포트·외부 전원이 확인된 RGB 컨트롤러를 추천하고, 견적에 추가한 뒤에도 같은 원문 기준으로 재검사합니다. 추가 쿨링팬과 허브를 함께 선택하면 3핀 DC·4핀 PWM·IDE/Molex 연결 타입을 대조하고, 허브 최대 허용전류와 개별 팬 소비전류가 모두 있을 때만 합산합니다. 연결 계획에는 허브 출력·팬 입력·외부 전원·계산된 전류 여유를 함께 보여주며, 허브가 여러 개이면 팬별 연결 대상 허브와 케이스 RGB 연결 컨트롤러를 지정하지 않은 상태를 별도로 표시하며, RGB 기능 허브가 여러 개면 컨트롤러를 하나 지정하기 전까지 RGB 연결 계획을 만들지 않습니다. 전류 근거가 하나라도 없으면 안전하다고 추정하지 않고 확인 필요로 남깁니다. UPS의 VA 용량은 역률 정보 없이 W로 임의 환산하지 않습니다. 저장장치 어댑터·M.2 방열판은 여러 SSD가 있는 견적에서 `연결 대상 SSD`를 지정할 수 있고, 지정하지 않은 legacy 입력은 선택한 M.2 SSD 전체를 대상으로 해석합니다. 저장장치 어댑터는 다른 디스크에 사용할 가능성이 있어 길이·신호 불일치는 주의로 안내하며, 대상 SSD나 지원 인터페이스가 없으면 확인 필요로 남깁니다. 주변 부품이나 기준이 되는 케이스·SSD가 아직 없거나 규격이 비어 있으면 호환으로 추정하지 않고 확인 필요로 남깁니다. 주변 부품 점검은 핵심 부품 호환 판정을 덮어쓰지 않지만 구매 준비도에 별도 항목으로 반영하고, 근거·실제값·기대값·수정 안내를 함께 제공합니다. 팬 모터 소비전류는 RGB LED 부하와 분리해 `팬 1개당 A`로 해석하며, 원문에 없을 때는 관리자 데이터 센터의 `쿨링팬 소비전류 검수`에서 제조사 모델·근거 메모·HTTPS 원문을 입력할 수 있습니다. 이 보강값은 원본 액세서리 파일과 분리된 override로 저장되고, coverage·허브 전류 합산·미지정 팬 허브 후보 추천에만 런타임 적용됩니다.

결과 화면의 `팬·RGB 연결 자원`은 케이스 기본 팬·RGB 장치 수와 메인보드 팬/RGB 헤더를 사용량·여유·부족으로 요약하고, 5V ARGB·12V RGB 전압별 헤더가 확인되지 않으면 별도 `확인 필요`로 표시합니다. 팬 허브나 RGB 컨트롤러가 필요할 수 있는 경우 관련 finding으로 바로 이동할 수 있으며, 추가한 주변 부품은 기본 케이스 자원과 섞어 계산하지 않습니다. 엔진 finding이 없는 연결 근거 누락도 `connectivity:*` 같은 ID로 우선 조치 액션센터에 표시하고 연결 자원 패널로 이동시키며, 완료 상태를 구매 전 체크리스트와 공유합니다. 연결 자원 상태와 누락 정보는 구매 전 체크리스트·텍스트 리포트·구조화 JSON 리포트에도 같은 근거로 기록합니다.

해결 플랜은 최소 변경·가성비·성능 유지 세 가지 기준으로 서로 다른 조합을 우선 제시합니다. 각 플랜은 후보 교체 또는 RAM·SSD·HDD 수량 조정 후 동일 규칙 엔진으로 재평가하며, 남은 오류가 있으면 이를 숨기지 않고 함께 표시합니다. RAM 용량·슬롯, M.2 슬롯, SATA 포트, HDD 베이처럼 수량·구성 조정이 핵심인 finding은 대체 부품이 없다는 식으로 오해시키지 않고 `수량·구성 조정 플랜` 안내를 표시하며 추천 플랜 영역으로 바로 이동할 수 있습니다. 플랜 카드와 비교표에는 `카탈로그 성능 기준 유지`·`성능 기준 변경`을 별도로 표시해 CPU·GPU·RAM·SSD·HDD 중 어떤 축을 유지하고 어떤 축을 바꾸는지 보여주며, 실제 FPS나 벤치마크 성능을 보장하는 표현은 사용하지 않습니다.

기존 3개 전략과 별도로 영향 카테고리별 후보를 제한된 beam search로 확장 탐색해 모든 차단·주의·확인 필요 항목이 사라지는 `완전 호환` 플랜을 찾습니다. 완전 조합이 있으면 별도 플랜으로 표시하고, M.2 슬롯·보조전원처럼 원문으로 확정할 수 없는 정보가 남으면 완전 호환으로 과장하지 않고 확인 필요 사유를 안내합니다. 탐색 폭은 후보 8개·beam 64개로 제한해 대규모 카탈로그에서도 응답 시간을 통제합니다.

각 수리 플랜에는 `적용 후 남는 문제`도 최대 3개까지 함께 표시합니다. 따라서 차단 오류가 줄었다는 숫자만 보고 플랜을 확정하지 않고, 남은 소켓·슬롯·전력·장착 위험을 플랜 선택 전에 확인할 수 있습니다. 오래된 API 응답에 이 필드가 없을 때도 기존 플랜 표시를 유지하도록 optional로 읽습니다.

잔여 문제 chip을 누르면 결과 상세의 해당 finding 카드로 이동합니다. 결과 필터가 `주의`·`확인 필요`처럼 좁혀져 있어도 먼저 `전체`로 복귀해 대상 카드가 렌더링된 뒤 이동하므로, 플랜 요약에서 보여준 다음 조치를 놓치지 않습니다.

수리 플랜이 2개 이상이면 `세 가지 플랜 한눈에 비교` 표를 먼저 보여줍니다. 변경 항목 수, 잔여 차단·주의·확인 필요, 적용 후 남는 문제, 가격 변화, 적용 후 합계, 목표 예산, 성능 근거를 한 열에 비교하고 `플랜 보기`를 누르면 해당 상세 카드로 이동합니다. 비교표는 lazy chunk로 분리해 초기 편집기 번들에 불필요한 로딩 부담을 더하지 않습니다.

결과 화면의 수리 플랜에는 `현재와 비교`가 제공됩니다. 선택한 플랜을 최신 카탈로그 기준으로 다시 계산해 현재 견적과 플랜 적용 후 견적의 호환 상태·위험 카운트·분석 점수·핵심/주변 금액·전체 부품과 수량·남은 finding을 나란히 보여줍니다. 비교 중에는 현재 견적을 바꾸지 않으며, 최신 현재 결과와 후보 가격을 다시 확인한 뒤 기존 변경 미리보기와 최종 재검사로 연결합니다. 가격이 불완전한 주변 부품은 `없음`과 `가격 확인 필요`를 구분해 표시합니다.

수리 플랜 전체 비교에는 `이 플랜을 새 견적으로 저장`도 제공됩니다. 사용자가 비교한 플랜은 기존 견적을 덮어쓰지 않고 별도 저장 다이얼로그로 전달되며, 저장 후에는 새 share ID·owner token·검사 snapshot을 발급받아 새 플랜 결과 화면을 엽니다. 공유 링크 복사에 실패해도 저장 결과와 링크 주소를 화면에 남깁니다.

수리 플랜으로 새 견적을 저장하면 원본 owner token이 있는 경우 원본 견적의 `versionGroupId`와 다음 `versionNumber`, `derivedFromBuildId`를 함께 기록합니다. 히스토리는 같은 버전 그룹을 `v1·v2·…`로 묶고 최신 두 버전을 현재 카탈로그 기준으로 다시 검사해 부품·수량·위험·금액을 비교합니다. 기존 메타데이터가 없는 legacy 저장 견적은 자체 `v1`로 해석하며, 원본 견적은 자동으로 수정하지 않습니다.

버전 번호 발급은 저장 직전 lineage별로 원자화합니다. PostgreSQL에서는 transaction advisory lock 안에서 다음 번호를 계산하고, JSON fallback에서는 `saved-build-version.lease`와 process-local mutation queue를 함께 사용합니다. 따라서 같은 원본에서 동시에 두 플랜을 저장해도 단일 서버 기준 `v2·v3` 순서를 유지하며, lease가 남으면 임의로 덮어쓰지 않고 재시도 오류를 반환합니다.

관리자 데이터 센터의 `저장 견적 버전 상태`는 모든 저장 견적을 읽기 전용으로 감사해 legacy fallback, 버전 번호 누락, 명시적 버전 그룹, 복수 버전 그룹, 중복 버전 키, 존재하지 않는 부모 견적, 다른 그룹을 가리키는 자식 견적을 구분합니다. 상태는 `무결성 정상`·`legacy 정리 필요`·`무결성 확인 필요`로 표시하며, `GET /api/admin/build-versions/status`는 같은 감사 결과를 관리자 인증 뒤에 제공합니다. `GET /api/admin/build-versions/migration-preview`는 legacy 행이 부모 그룹을 상속할 때의 예상 그룹·버전 번호와 차단 사유, 최신 저장 데이터 fingerprint를 계산합니다. 프리뷰가 `ready`일 때만 관리자 확인 문구와 동일한 fingerprint를 요구하는 `POST /api/admin/build-versions/migrate`가 원자적으로 적용하며, JSON backup 또는 PostgreSQL backup table을 먼저 남깁니다. `GET /api/admin/build-versions/backups`는 최근 backup 5개의 요약과 현재 fingerprint 기준 `rollbackAvailable`을 제공하고, `GET /api/admin/build-versions/last-backup`은 그중 최신 항목을 호환용으로 반환합니다. `GET /api/admin/build-versions/backups/{backupId}`는 선택한 backup의 버전 그룹·버전 번호·부모 연결 diff만 반환해 상세 검수에 사용합니다. 두 API 모두 backup snapshot 자체나 owner token hash는 노출하지 않습니다. 적용 후 저장 데이터가 바뀌면 rollback을 차단하고, `POST /api/admin/build-versions/rollback`은 backup ID·적용 후 fingerprint·확인 문구가 모두 맞을 때만 선택한 적용을 복원합니다. 운영 화면의 새로고침과 프리뷰 계산은 실제 저장을 수행하지 않습니다.

호환성 검사와 자동 구성 요청은 일시적인 네트워크·5xx 응답에 한해 제한적으로 재시도하며, 저장 POST는 중복 저장을 막기 위해 자동 재시도하지 않습니다. 검사 실패 시 입력한 견적과 마지막 성공 검사 결과를 유지하고 화면에서 다시 시도할 수 있습니다.

부품 선택기와 주변 부품 카탈로그도 조회 실패를 화면에 남기고 `다시 불러오기`를 제공합니다. 검색어·필터·현재 선택 상태는 유지되며, 새 검색이나 재시도가 이전에 늦게 도착한 응답으로 현재 목록을 덮어쓰지 않도록 요청 세대를 확인합니다. 목록의 다음 페이지를 불러오다 실패한 경우에도 전체 결과를 지우지 않고 해당 배치만 다시 요청할 수 있습니다.

부품 선택기에서 `차단 오류 없는 후보` 또는 `확인된 안전 후보`를 선택하면 현재 견적에 후보를 임시 적용해 후보 자체의 위험도를 미리 확인합니다. 전자는 새 차단 오류만 막고 스펙 확인이 필요한 후보를 포함하며, 후보별로 `차단 없음 · 확인 필요` 또는 `호환 확인`을 구분해 표시합니다. 후자는 새 차단 오류와 확인 필요 항목을 모두 막습니다. 전체 카탈로그 모드도 그대로 제공하며, 안전 후보가 없을 때 그 이유를 안내합니다.

호환 후보 선택기의 `교체 예산`은 후보의 추천 수량을 반영한 총액으로 필터링합니다. 예산 초과·가격 미확인 후보를 제외한 개수를 별도로 보여 주며, 예산을 비우면 기존 안전 후보와 유사도 정렬 결과를 그대로 탐색할 수 있습니다.
CPU 선택기에서 `벤치마크 근거 포함`을 선택하면 Cinebench R23 기반 또는 벤치마크와 확인 스펙을 함께 사용한 후보만 남깁니다. 이때 서버 메타데이터의 Cinebench coverage와 후보 제외 수를 함께 표시하며, GPU·케이스처럼 연결된 벤치마크가 없는 범주는 후보가 없을 수 있음을 안내합니다.

호환 후보 선택기의 `성능 기준`은 서버에서 전체 호환 후보를 먼저 계산한 뒤 `전체 성능 후보`·`동급·유사만`·`근거 충분만`·`벤치마크 근거 포함`으로 좁힙니다. `벤치마크 근거 포함`은 Cinebench R23이 포함된 CPU 비교처럼 벤치마크 또는 벤치마크와 확인 스펙을 함께 사용한 후보만 남기며, GPU처럼 현재 벤치마크 데이터가 없는 범주는 후보가 없을 수 있음을 명시합니다. 성능 기준으로 제외된 후보 수를 별도로 표시하고, 조건을 만족하는 후보가 없으면 성능 필터 때문인지 호환 후보 자체가 없는지 구분해 안내합니다. 이 필터는 현재 페이지 일부만 잘라내지 않고 전체 결과 수와 페이지네이션을 함께 갱신합니다.

부품 선택기의 카테고리별 스펙 필터는 서버 전체 카탈로그에 적용됩니다. GPU는 최소 VRAM, RAM은 최소 킷 용량·메모리 속도, SSD/HDD는 최소 용량·NVMe/SATA 연결 방식, 파워서플라이는 최소 정격 출력을 지정할 수 있으며, 스펙을 확인하지 못한 상품은 조건을 만족한다고 추정하지 않고 제외합니다. 필터 결과 수와 스펙 조건으로 제외된 수를 함께 표시하고, 다음 페이지에도 같은 조건을 유지합니다.

부품 선택기에는 `데이터 갱신` 필터를 추가해 최근 확인(3일 이내)·갱신 권장(14일 이내)·오래된 정보·시점 확인 필요를 전체 카탈로그와 호환 후보에서 구분합니다. 서버가 계산한 갱신 상태와 제외 수를 응답에 포함하며, 후보 비교표·공유 snapshot·CSV/JSON export에도 같은 상태를 전달합니다. 이 상태는 호환성 보장이 아니라 가격·스펙 원문을 다시 확인할 우선순위를 나타냅니다.

가격 상태도 `전체 가격 상태`·`가격 확인 상품만`·`가격 미확인 상품만`으로 필터링할 수 있습니다. 가격 미확인 후보를 자동으로 최저가처럼 취급하지 않으며, 후보 비교·구매 목록에서는 가격 상태와 유통 조건(신품·정식 유통, 벌크, 병행수입 등)을 함께 표시합니다.

주변 부품 카탈로그도 같은 `데이터 갱신` 필터를 사용하며, 팬·방열판·그래픽카드 지지대·팬 허브·UPS를 포함한 액세서리 API가 결과별 갱신 상태와 제외 수를 반환합니다. 주변 부품을 견적에 추가하면 추천 카드·구매 목록·구매 목록 CSV/복사 결과에도 해당 상태를 남겨, 핵심 부품과 주변 부품의 원문 확인 기준을 일관되게 유지합니다.

후보 필터 아래에는 검색 조건에 맞는 전체 후보의 `안전 · 확인 필요 · 제외` 분포도 표시합니다. 결과가 0개여도 원래 후보가 없었던 것인지, 스펙 부족으로 확인 필요 후보만 남았던 것인지, 명백한 차단 오류로 제외됐는지 구분할 수 있습니다.

호환 후보에는 `추천 후보`·`확인 후 적용`·`적용하지 않음` 판단 요약을 함께 표시합니다. 후보 자체의 위험도뿐 아니라 현재 문제 해결 여부, 추천 근거 수준, 물리 근거, 데이터 갱신 상태를 조합해 계산하며, 오래된 데이터·시점 불명·물리 근거 확인 필요 후보는 자동으로 확인 후 적용으로 낮춥니다. 이 요약은 호환성 보증이 아니라 후보를 먼저 읽을 순서를 정하는 결정 보조입니다.

후보를 2~3개 비교할 때는 `빠른 선택` 기준을 `균형`·`호환 우선`·`성능 우선`·`가격 우선`·`근거 우선`으로 전환할 수 있습니다. 각 기준은 적용 가능한 후보만 따로 순위화하고, 차단 후보는 제외 수로 표시합니다. `1위 후보 적용`은 사용자가 버튼을 눌렀을 때만 기존 변경 미리보기·재검사 흐름으로 이어지며, 기준을 바꾸는 것만으로 현재 견적은 변경하지 않습니다.

호환 후보 모드에서는 현재 구성의 선택 부품과 후보를 같은 카테고리 안에서 비교하는 `유사도 높은 순` 정렬을 제공합니다. 후보 목록에는 유사도 점수·동급/유사/대안 등급·공통 스펙 coverage·핵심 스펙 변화 요약을 표시하며, 점수가 같으면 근거 수준과 coverage가 높은 후보를 먼저 표시합니다. 전체 카탈로그 모드는 현재 구성과 무관한 검색이므로 유사도 정렬을 제공하지 않습니다.

부품 선택 카드에서도 검사 전 상세 스펙을 펼쳐 정규화된 값, 데이터 품질, 가격 확인 여부, 갱신일, 누락 필드, 저장된 원문 스펙과 허용된 원문 링크를 확인할 수 있습니다. 선택 직후 필요한 부품 상세를 자동으로 불러오며, 조회에 실패해도 선택 ID와 편집 상태는 유지합니다.

호환 후보 선택기에서는 후보를 바로 적용하기 전에 `상세·근거`를 열어 정규화된 스펙·가격·갱신일·원문·성능 비교 근거를 확인할 수 있습니다. 상세 확인은 선택 상태를 바꾸지 않으며, 실제 적용은 후보 행을 별도로 눌러야 합니다.

호환 후보 선택기에서는 최대 3개 후보를 `비교`로 선택해 적용 전에 가격·성능 유사도·성능 변화·호환 상태·데이터 품질을 나란히 확인할 수 있습니다. 비교 선택과 `상세·근거` 확인은 현재 견적에 후보를 적용하지 않으며, 후보 행 또는 비교표의 `이 후보 적용` 버튼을 별도로 눌렀을 때만 교체가 실행됩니다.

후보 비교표의 `공유 링크`는 2~3개 후보 snapshot을 서버에 저장하고 `/compare/{id}` 읽기 전용 화면을 제공합니다. 생성 링크는 30일 뒤 만료되며, 생성자에게만 반환된 owner token으로 현재 비교표에서 공유를 취소할 수 있습니다. 공유받은 사용자는 후보 가격·성능·호환 근거를 볼 수 있지만 현재 견적에 후보를 자동 적용할 수 없습니다. 서버 공개 응답에서는 owner token hash를 제거하고, 원문 링크는 허용된 HTTPS 다나와 주소만 보존합니다.

대체 후보·호환 유지 업그레이드 후보·부품 선택기의 후보 카드에는 `가격 추적`을 바로 등록하는 동작을 제공합니다. 등록 항목은 가격 추적 화면과 같은 브라우저 관심 목록에 중복 없이 저장하고, 카드에서는 `추적 중` 상태를 즉시 표시합니다. 목표가와 가격 하락·확인 상태 알림 조건은 가격 추적 화면에서 별도로 설정하며, 후보를 견적에 적용하지 않아도 가격을 지켜볼 수 있습니다.

대체 후보는 현재 문제를 해결하는 것뿐 아니라 교체 후 구성에 새 차단 오류나 확인 필요 항목을 추가하지 않는지도 다시 검사합니다. 현재 카탈로그에 그런 후보가 없으면 억지로 `동급` 후보를 제시하지 않고 안전한 대체 후보가 없다고 안내합니다. 유사도 점수 옆에는 현재와 후보 양쪽에서 실제로 비교된 공통 스펙 개수와 근거 수준을 표시하며, 실제 벤치마크 순위가 아닌 카탈로그 상대 스펙이라는 경계를 유지합니다. 후보의 `근거`를 열면 항목별 현재값·후보값·점수·가중치를 확인할 수 있고, 비교표에서는 현재 선택 부품을 기준 열로 함께 보여 소켓·용량·슬롯·가격 변화를 바로 확인할 수 있습니다. 선택한 CPU·GPU의 성능 스펙이 부족하면 동일 CPU·GPU 모델 계열의 검증된 카탈로그 참조를 제한적으로 사용하고, 참조 사용 사실과 유사 성능 후보 부재를 화면·근거에 명시합니다.

대체 후보·호환 유지 업그레이드 카드의 `가상 적용`은 후보를 현재 전체 견적에 비파괴적으로 대입해 실제 호환성 규칙을 한 번 더 계산합니다. 현재 구성과 가상 구성의 판정·차단·주의·확인 필요·총액 변화를 나란히 보여주며, 위험이 줄어도 확인 필요 항목이 늘어난 경우 이를 별도로 경고합니다. 가상 검증만으로는 현재 선택·검사 결과·저장 견적을 바꾸지 않고, 사용자가 `이 구성 적용 후 다시 검사`를 눌렀을 때 기존 변경 미리보기와 최종 확인을 거칩니다.

유사도 거리는 현재값과 후보값 중 큰 값을 기준으로 대칭 정규화해, 같은 폭의 상향·하향 변화가 방향에 따라 다른 점수가 되지 않도록 합니다. GPU 계열이 다르면 아키텍처 의존적인 스트림 프로세서 수를 비교에서 제외하고, 제외된 항목과 이유를 근거에 남깁니다.

결과 화면의 대체 후보 비교표에서도 `전체 가상 비교`를 실행할 수 있습니다. 한 finding에서 고른 최대 3개 후보를 각각 현재 전체 견적에 독립적으로 대입해 호환 상태·차단·주의·확인 필요·총액·잔여 finding을 나란히 보여주며, 추천 후보가 이미 해결한 문제 외에 다른 기존 문제가 남아 있어도 후보 자체의 안전성과 전체 결과를 혼동하지 않습니다. 결과 후보는 실제 적용 전에 동일한 변경 미리보기와 최종 재검사를 거치며, 안전한 후보는 현재 견적을 덮어쓰지 않고 `새 견적으로 저장`해 별도 공유 링크와 버전 계보로 보존할 수 있습니다.

앱 시작 시 부품 목록·서비스 메타데이터·저장 견적을 독립적으로 동기화합니다. 일부 요청이 실패해도 편집기는 계속 사용할 수 있고, 상단 안내에서 실패한 초기 동기화를 다시 요청할 수 있습니다. 초기 부품 목록은 이미 불러온 선택 부품 상세와 병합해 늦게 도착한 목록 응답이 상세 정보를 덮어쓰지 않도록 합니다.

저장 견적을 열 때 선택 상세가 현재 부품 목록에 없으면 `/api/parts/batch`와 `/api/accessories/batch`로 필요한 ID를 각각 한 번에 조회합니다. 두 API는 공백 정리·중복 제거·최대 100개 제한·요청 순서 보존·`missingIds` 응답을 제공하며, 하나의 상세가 없어도 나머지 선택 부품은 함께 보강합니다. 기존의 단건 상세 API는 원문 확인·공개 상세 조회 용도로 유지합니다. 이를 통해 여러 선택 부품을 순차적으로 조회하며 화면 전환을 지연시키지 않고, 저장 견적 열기와 전체 호환성 결과 캐시를 독립적으로 검증할 수 있습니다.

CPU 상세 원문에서 확인되는 Cinebench R23 싱글·멀티 점수도 정규화해 CPU 대체 후보와 자동 구성의 상대 지수에 반영합니다. 점수가 없는 CPU를 임의로 추정하지 않으며, 싱글·멀티 또는 코어·스레드 중 일부만 확인된 후보는 유사도 근거 수준을 낮춰 표시합니다. 이 값 역시 실제 모든 작업의 성능을 보장하는 벤치마크 순위가 아니라 저장된 원문 기준의 참고값입니다.

후보 카드의 유사도 근거에는 비교에 사용한 기반도 함께 표시합니다. Cinebench R23 점수가 포함된 CPU 비교는 `Cinebench R23 기반`, R23와 코어·클럭 등 확인 스펙을 함께 사용한 경우는 `벤치마크·확인 스펙 기반`, GPU·메모리·저장장치 등은 `확인 스펙 기반`으로 구분해 실제 벤치마크와 카탈로그 스펙을 혼동하지 않도록 했습니다.

GPU 상세 원문에서 확인되는 부스트 클럭·스트림 프로세서·VRAM 대역폭도 그래픽카드 대체 후보의 스펙 유사도 비교에 반영합니다. NVIDIA·AMD·Intel 계열과 RTX 50·RTX 40·RX 90 같은 세대 계열을 원문에서 구분하며, 서로 다른 GPU 아키텍처의 스트림 프로세서 수는 직접 비교하지 않고 그 제외 이유를 근거 패널에 남깁니다. 전력·권장 파워·장착 치수는 유사도 점수가 아니라 별도의 호환성 기준으로 검사합니다. 원문에 없는 수치는 추정하지 않고 근거 coverage를 낮춰 표시합니다.

GPU 원문에서 GDDR5·GDDR6·GDDR6X·GDDR7·HBM 메모리 타입을 정규화해 상세 카드와 후보 비교에 표시합니다. 현재 원문에 메모리 버스 폭이 안정적으로 제공되지 않아 추정하지 않습니다.

GPU 원문에 `3DMark Time Spy` 또는 `3DMark Port Royal` 점수가 명시되어 있으면 선택 부품의 GPU 유사도·업그레이드 비교에 선택적으로 반영하고, `벤치마크 근거 포함` 필터와 coverage에 연결합니다. 값이 없으면 GPU 스펙을 벤치마크로 포장하지 않으며, 재파싱 시 이전 원문에서만 존재하던 stale 점수도 제거합니다.

관리자 데이터 센터의 `검수된 성능 데이터 보강`에서 원문에 없는 검증 점수를 JSON으로 입력할 수 있습니다. CPU·GPU별 허용 필드, 양수 정수 범위, 근거 메모, HTTPS 출처 URL, 중복 부품 ID를 서버에서 먼저 검증하며 한 항목이라도 오류가 있으면 전체 저장을 중단합니다. 저장된 보강은 PostgreSQL이 연결된 환경에서는 `benchmark_overrides` 테이블에, 연결되지 않은 환경에서는 원자적 JSON fallback에 저장하고 원문 파싱 결과 위에 별도 overlay로 적용합니다. 따라서 다음 원문 재수집에도 유지되며, 삭제하면 원문에 실제로 존재하는 점수만 다시 사용합니다.

보강 패널의 `ROW BUILDER`에서 CPU·GPU를 모델명으로 검색해 부품을 선택하고, 범주에 맞는 점수 입력칸과 검수 근거를 채운 뒤 현재 JSON batch에 행을 추가할 수 있습니다. 같은 partId의 기존 행은 교체하며, 행 추가만으로 저장하지 않고 서버 JSON 검증을 다시 통과해야 실제 저장 버튼이 활성화됩니다.

서버 검증 결과에는 각 행의 `신규 등록`·`기존 값 수정`·`변경 없음`을 미리 표시하고, 수정되는 벤치마크 필드와 근거 메타데이터를 함께 보여줍니다. 저장소 상태도 해당 패널에서 PostgreSQL 또는 JSON fallback으로 구분해 운영자가 저장 위치를 오인하지 않도록 했습니다.

저장된 보강 목록은 부품명·partId·검수 근거·출처 URL 검색과 CPU/GPU 범주·출처 유형 필터를 지원합니다. 목록 필터는 저장된 원본을 변경하지 않고 화면 표시만 좁히며, 결과가 없을 때 전체 데이터가 없는 경우와 검색 조건이 맞지 않는 경우를 구분해 안내합니다.

벤치마크 보강 패널은 스프레드시트에서 복사한 CSV를 JSON batch로 변환하고, 저장된 보강을 인용부호·쉼표·줄바꿈까지 보존한 CSV로 내보냅니다. CSV 변환 후에도 JSON 서버 검증과 신규·수정·변경 없음 미리보기를 다시 통과해야 저장할 수 있습니다.

호환 대체 후보·부품 선택기·업그레이드 후보에는 `추천 근거 신뢰도`를 함께 표시합니다. 이 값은 성능 보장이나 구매 보증이 아니라, 전체 구성 재검사 결과, 비교 가능한 스펙 범위, 벤치마크 포함 여부, 후보 데이터 품질, 갱신 상태, 가격·원문 확인 여부를 합산한 근거 완성도 지수입니다. `높음·보통·낮음` 등급과 점수뿐 아니라 남은 확인 필요·누락 스펙·가격 미확인 사유를 함께 보존하며, 후보 비교 텍스트·CSV·JSON·공유 링크에도 전달하며, GPU·케이스·PSU 후보의 물리 검수 상태와 확인된 GPU·케이스·PSU 출처 메모·HTTPS 원문 링크를 별도 보존합니다. 출처 메타데이터가 없는 숫자값은 물리 근거 `확인됨`으로 승격하지 않습니다.

부품 선택기의 `추천 근거` 필터는 `전체 근거`·`보통 이상`·`높음만`을 지원합니다. 필터링 전 후보 수와 신뢰도 조건으로 제외된 수를 서버가 함께 반환하고, 결과가 없으면 조건을 낮춰 호환 우선 후보를 다시 확인하도록 안내합니다.

추천 신뢰도에서 `후보 호환 검증`과 `전체 견적 상태`를 분리합니다. 후보 호환 검증은 해당 후보가 새 차단 오류·확인 필요를 만드는지 기준으로 계산하고, 전체 견적 상태는 후보를 적용한 뒤에도 남아 있는 기존 오류를 별도 수치로 표시합니다. 따라서 복잡한 견적에서도 안전한 대체 후보가 다른 기존 오류 때문에 사라지지 않습니다.

대체 후보 정렬은 추천 우선순위를 보존합니다. 균형형은 동일한 호환 해결 범위에서 추천 근거 신뢰도·비교 범위·유사도·가격 순으로 좁히고, 성능 우선과 가성비 우선은 각각 성능 변화와 가격 기준을 먼저 적용한 뒤 신뢰도를 동점 보정으로 사용합니다.

관리자 데이터 센터의 `먼저 채울 벤치마크 데이터` 큐는 CPU·GPU의 미완전 점수 세트를 부분·미등록 상태로 나누고, 데이터 품질·가격·원문 확인 가능성을 기준으로 우선순위를 계산합니다. 완전한 점수 세트라도 벤치마크 확인 시점이 14일을 넘었거나 없으면 `갱신 필요` 큐에 다시 올리고, 최근·갱신 권장·갱신 필요·시점 불명의 신선도와 기존 출처 유형을 함께 표시합니다. CPU와 GPU를 교차 배치한 최대 100개 목록과 빈 근거 필드의 CSV 검수 템플릿을 제공하며, 템플릿은 기존 점수만 보존하고 검수 메모·출처 URL은 비워 두어 출처를 추정하지 않습니다.

검수 큐는 CPU·GPU 범주와 점수 없음·일부 점수 상태로 다시 좁혀 볼 수 있습니다. 개별 `JSON에 추가`는 기존 batch에서 같은 partId를 중복 생성하지 않고 기존 점수·근거 메모·출처 URL을 보존한 채 큐의 확인 점수만 병합합니다. 잘못된 batch 구조는 기존 JSON을 버리지 않고 추가를 차단합니다.

벤치마크 보강 패널은 CSV를 직접 붙여넣는 방법과 `.csv` 파일을 선택해 가져오는 방법을 모두 지원합니다. 두 입력 경로는 같은 인용부호·줄바꿈·점수 파서를 사용하고, 파일을 읽는 단계에서는 저장하지 않으며 JSON 서버 검증을 통과한 뒤에만 저장 버튼을 활성화합니다.

벤치마크 보강에는 `sourceKind`를 선택적으로 기록할 수 있습니다. `official`은 제조사·공식 측정표, `independent_review`는 독립 리뷰·벤치마크 DB, `community_measurement`는 사용자 실측, 누락된 legacy 값은 `other`로 표시합니다. sourceKind가 없는 기존 저장값도 계속 읽되 출처 유형 미분류로 처리하며, 분류된 벤치마크는 추천 근거 신뢰도에 출처 가중치를 반영합니다. 원문을 다시 파싱할 때는 임시 overlay의 provenance를 제거한 뒤 저장된 benchmark override를 다시 적용해 stale 출처가 남지 않게 합니다.

출처 분류 검수 큐는 점수가 하나 이상 있지만 provenance가 없는 CPU·GPU를 점수 누락 큐와 분리해 보여줍니다. 완전 세트·부분 점수의 확인값을 보존한 별도 CSV 템플릿과 `JSON에 추가` 버튼을 제공하며, 기존 점수를 다시 추정하지 않고 공식·독립 리뷰·사용자 실측 근거를 운영자가 입력하도록 합니다.

관리자 데이터 센터의 벤치마크 coverage에는 점수가 하나 이상 확인된 CPU·GPU를 출처 유형별로 나눠 보여줍니다. 명시적으로 분류된 점수와 아직 provenance가 없는 원문 점수를 분리해, 추천 신뢰도에 사용할 수 있는 근거의 범위를 과장하지 않습니다.

SSD 원문에서 컨트롤러·NAND 타입·TBW·읽기/쓰기 IOPS를 정규화합니다. IOPS는 SSD 대체 후보의 유사도에 반영하고 TBW·컨트롤러·NAND는 상세 정보와 비교표에 표시하되, TBW는 제조사 표기 내구성 참고값이지 실제 수명 보장이 아닙니다.

M.2 NVMe SSD 원문에서 PCIe 2~6세대 표기를 정규화하고, 메인보드 `M.2 연결` 원문에 확인된 세대 목록과 비교합니다. SSD 세대가 더 높으면 장착 자체를 차단하지 않고 메인보드에서 확인된 가장 높은 세대로 링크되는 성능 주의로 표시합니다. 이 주의의 대체 후보는 같은 NVMe M.2 범위에서 메인보드 세대 상한 이하인 SSD를 우선 추천하고, 자동 구성도 확인된 세대 상한을 넘는 SSD를 제외합니다. 슬롯별 세대·레인 배치는 원문만으로 확정하지 않으므로 제조사 매뉴얼 확인이 필요할 수 있습니다.

메인보드가 M.2 PCIe 세대를 두 종류 이상 집계해서 제공하고 다중 M.2 SSD를 선택하면 `M.2 슬롯별 PCIe 세대 배치를 확정할 수 없습니다`를 확인 필요로 표시합니다. 엔진은 M2_1·M2_2·M2_3의 세대·CPU 직결·레인 공유를 임의로 배정하지 않으며, 제조사 매뉴얼에서 슬롯별 연결 조건을 확인하도록 안내합니다. 같은 세대가 확인된 보드나 단일 M.2 구성에는 이 확인 필요를 추가하지 않습니다.

관리자 데이터 센터에서는 제조사 매뉴얼을 근거로 메인보드별 M2_1~M2_8 슬롯의 지원 인터페이스, PCIe 세대, CPU 직결·칩셋 연결, 공유 대상과 출처 메모·HTTPS URL을 별도 override로 등록할 수 있습니다. override는 수집 원문과 별도로 저장되며, 슬롯 수·슬롯 번호·세대·인터페이스 입력을 서버에서 검증합니다. 모든 슬롯의 필수 정보가 등록되면 엔진이 SSD를 슬롯에 자동 배치하고 실제 링크 세대를 계산하며, 인터페이스가 맞지 않으면 장착 차단, 공유 대상이 활성화되면 확인 필요를 표시합니다.

슬롯 override가 등록된 메인보드와 M.2 SSD를 선택하면 편집기에서 슬롯별 SSD 배치를 직접 지정할 수 있습니다. 모든 슬롯을 비워 두면 엔진이 PCIe 세대·인터페이스 조건을 기준으로 자동 배치하고, 하나라도 수동 지정하면 선택한 M.2 SSD 수량에 맞춰 슬롯을 모두 지정해야 합니다. 지정한 SSD가 슬롯 인터페이스와 맞지 않거나, 선택 수량·슬롯 수·SSD ID가 현재 구성과 다르면 수동 배치를 무시하지 않고 차단 오류로 표시합니다. SSD·메인보드·수량을 바꾸면 이전 수동 배치는 자동으로 초기화하며, 결과에는 자동 배치인지 수동 지정 배치인지와 실제 링크 PCIe 세대를 구분해 표시합니다.

관리자 데이터 센터의 일괄 관리에서는 검수된 `{items: [...]}` JSON을 먼저 카탈로그와 대조해 미리 검증하고, 모든 항목이 통과한 경우에만 한 번의 원자적 저장으로 여러 메인보드 매핑을 추가·갱신합니다. 보드 ID 누락·중복·슬롯 수/번호 오류·지원 인터페이스·PCIe 세대·HTTPS 출처 오류가 하나라도 있으면 유효한 항목까지 저장하지 않습니다. 현재 저장된 매핑은 JSON으로 내보내 다른 환경에서 같은 포맷으로 재검증할 수 있습니다.

관리자 데이터 센터의 매핑 커버리지에서는 M.2 슬롯이 확인된 전체 메인보드를 대상으로 매핑 완료·재검수·불완전·미등록 수, 다중 슬롯 수, 복수 PCIe 세대 집계 수, 슬롯 수별 분포와 커버리지율을 계산합니다. 완전한 수동 매핑이라도 카탈로그 원문 갱신 시점이 매핑 검수 시점보다 최신이면 `재검수`로 분리해 유효 완료 커버리지에서 제외하고 검수 큐에 다시 올립니다. 미등록·재검수·불완전 보드는 다중 슬롯·복수 PCIe 세대·누락된 연결 정보처럼 실제 데이터 복잡도가 높은 순서로 검수 큐에 올리며, 이는 판매량이나 인기 순위가 아닌 매뉴얼 확인 난이도 기준입니다. 큐에서 보드를 선택하면 단건 매핑 편집기로 이동합니다.

검수 큐에서는 미등록·불완전 보드의 `M2_1~M2_n` 검수 템플릿을 최대 100개까지 JSON으로 생성할 수 있습니다. 미등록 보드는 슬롯 ID만 생성해 제조사 매뉴얼 확인을 요구하고, 불완전 매핑은 이미 확인된 인터페이스·PCIe 세대·연결 주체·공유 대상만 보존한 채 누락된 값은 추정하지 않습니다. 생성된 템플릿은 매뉴얼 값을 채운 뒤 기존 일괄 검증 API에 다시 넣을 수 있습니다.

관리자 화면의 M.2 검수 테이블에서는 상위 20개 검수 보드를 행 단위로 직접 편집할 수 있습니다. 슬롯별 인터페이스·PCIe 세대·연결 주체·공유 대상을 입력하고, `공유 없음 확인`을 별도로 눌러야 빈 공유 필드를 확정할 수 있습니다. 서버 검증 후 완전한 보드만 `완전 행 저장`으로 원자 저장하며, 보완이 필요한 행과 원문 갱신으로 재검수가 필요한 행은 검수 큐에 남겨 작업을 이어갈 수 있습니다.

검수 테이블은 슬롯 한 행 단위의 CSV도 지원합니다. CSV 내보내기는 현재 표를 스프레드시트에서 검수할 수 있도록 만들고, CSV 가져오기는 같은 메인보드의 슬롯 행을 자동으로 묶어 표에 반영합니다. 쉼표·줄바꿈·따옴표가 포함된 매뉴얼 메모, `공유 없음`으로 확정한 값, 아직 확인하지 않은 빈 값을 구분하며, 가져온 데이터도 반드시 서버 batch 검증과 완전성 검사를 통과해야 저장됩니다.

검수 테이블에서는 파일 선택 없이 CSV 내용을 직접 붙여 넣을 수도 있습니다. 스프레드시트에서 슬롯 행을 복사해 붙여 넣으면 현재 표 draft를 교체하고, 같은 서버 검증·완전 행 저장 흐름을 사용합니다.

대체 후보에는 현재 부품과 후보의 가격·유사도에서 계산한 `가격 대비 유사도`도 표시합니다. 현재와 후보 가격·비교 스펙을 모두 확인할 수 있을 때만 계산하며, 현재와 같은 성능·가격을 100점으로 보고 더 저렴하고 유사한 후보일수록 최대 200점까지 높아집니다. 화면과 API 근거에는 `n/200점` 스케일을 명시합니다. 가격이나 비교 스펙이 확인되지 않으면 가성비 점수를 추정하지 않고 `산정 불가`로 남깁니다. 호환 후보 선택기에서는 `유사도 높은 순`과 별도로 `가성비 높은 순`을 제공하고, 결과 카드·근거·비교표에서도 계산 기준과 가격 변화율을 확인할 수 있습니다.

SSD·HDD를 문제 해결 후보로 제안할 때는 현재 저장장치의 용량 이상과 같은 물리 폼팩터를 우선 요구합니다. M.2 2280을 선택한 구성에는 U.2나 M.2 2242처럼 실제 장착 조건이 달라지는 후보를 추천하지 않으며, 현재 용량보다 작은 저장장치는 후보에서 제외합니다. 현재 저장장치의 용량 또는 폼팩터 정보가 부족하면 해당 조건을 임의로 추정하지 않습니다.

결과 화면의 부품 교체 액션은 해당 오류의 규칙 ID와 영향받은 부품 ID를 후보 선택기까지 전달합니다. 선택기는 문제를 실제로 해결하는 후보를 기본으로 불러오고 유사도 높은 순으로 정렬하며, 사용자가 후보를 선택하면 기존 부품을 추가하지 않고 문제 대상 부품을 교체합니다. 여러 SSD·RAM·HDD를 선택한 구성에서 한 항목만 오류를 일으킨 경우에는 정상 항목을 유지하고 영향받은 항목만 바꿉니다. 결과에서 들어온 문제 해결 후보는 적용 직후 같은 구성으로 자동 재검사하고, 검사 실패 시에도 새로 선택한 입력과 마지막 성공 결과를 유지합니다. 필요하면 선택기에서 전체 카탈로그로 전환해 직접 탐색할 수 있습니다.

호환 후보 선택기에서 `교체 예산`을 입력하면 안전 후보·차단 오류 없는 후보를 후보의 추천 수량까지 곱한 총액으로 제한합니다. 예산 초과 후보와 가격 미확인 후보는 예산 결과에서 제외한 수를 함께 표시하며, 예산을 입력하지 않으면 기존 후보 탐색 결과를 그대로 유지합니다. 메모리처럼 킷 수량이 필요한 후보는 1킷 가격이 아니라 실제 추천 킷 전체 금액을 선택기 가격과 예산 기준에 사용합니다.

주변 부품 카탈로그에서는 추천 후보가 아니더라도 4천여 개 상품을 직접 검색해 현재 견적에 추가할 수 있습니다. 범주·데이터 상태·가격대·정렬을 함께 적용해 필요한 상품만 좁힐 수 있습니다. 추가한 상품은 카탈로그·편집기·결과·저장·공유 화면에서 같은 선택 상태로 유지되며, 견적 보기 버튼으로 편집기로 이동할 수 있습니다.

견적 작성 화면과 결과 화면에서 사용 목적, 게이밍 목표 해상도, 추천 우선순위, 목표 예산을 지정할 수 있습니다. 사용 목적과 해상도는 실제 벤치마크 수치가 아닌 카탈로그에 확인된 스펙의 비교 가중치·권장 VRAM 기준으로 사용됩니다. 예산은 추천 정렬과 초과 금액 표시의 기준이며, 실제 호환성 판정 자체를 완화하지 않습니다.

대체 부품 추천은 기본적으로 신품·정식 유통 후보만 사용합니다. 결과 화면의 구매 조건에서 벌크 포함 또는 전체 조건을 선택하면 후보 범위를 넓힐 수 있으며, 벌크·병행수입·해외구매·중고 후보는 상품별 유통 배지를 함께 표시합니다.

사용 목적은 일반형·게이밍·작업·크리에이터·개발·AI·사무·일반으로 제공됩니다. 게이밍은 GPU VRAM·그래픽 처리 여유·메모리 속도, 작업·크리에이터는 CPU 코어·스레드·메모리 용량·SSD 쓰기, 개발·AI는 CPU 병렬성·메모리·저장장치 용량을 더 중요하게 비교합니다. 이 값은 추천 순서와 설명에만 영향을 주며, 호환 규칙을 통과시키거나 완화하지 않습니다.

`POST /api/builds/recommend`는 현재 확인된 가격과 필수 호환 스펙만 사용해 CPU·쿨러·메인보드·RAM·SSD·케이스·PSU, 그리고 요청 시 GPU와 HDD를 포함한 초안을 생성합니다. 구성 우선순위(균형형·가성비 우선·성능 우선), RAM 목표 용량(16·32·64·128GB), SSD 최소 용량, HDD 용량·개수, 외장 GPU 포함 여부를 입력할 수 있습니다. 가성비 우선은 유효한 예산 내에서 더 저렴한 조합을 먼저 고르고, 성능 우선은 예산 내 유효 조합 중 카탈로그 상대 역량 점수가 높은 조합을 우선합니다. RAM 목표는 2개 구성의 실제 모듈 용량이 요청값 이상인지 서버에서 보장합니다. 게이밍 프로필에서 외장 GPU를 포함하면 선택한 해상도의 권장 VRAM 충족·미달·확인 필요 상태를 생성 결과에 표시하고, 미달·미확인 정보는 경고로 남깁니다. 해당 용량을 만족하는 확인된 킷이 없으면 부족한 초안을 조용히 반환하지 않고 생성 실패로 안내합니다. 중고·해외구매·벌크 상품은 기본적으로 제외하며, 요청 시에만 포함합니다. 생성 후에는 기존 편집기로 가져가거나 바로 호환성 검사를 실행할 수 있습니다. 예산 내 조합을 먼저 탐색하고, 예산 내 완전한 조합이 없을 때만 초과 금액을 명시합니다.

같은 조건에서 `균형형`·`가성비 우선`·`성능 우선` 세 가지 우선순위를 한 번에 비교하는 `3안 비교`도 제공합니다. 각 안은 독립적으로 생성·검증하며, 일부 기준만 실패하면 성공한 안과 실패 이유를 함께 표시합니다. 비교 결과가 같은 부품 조합이면 `구성 1종`·`동일 구성`으로 명시해 근거 없이 차이를 만들지 않습니다. 비교표에서 예상 합계·예산 여유·차단 오류·주의·확인 필요와 주요 부품 구성을 나란히 확인한 뒤 원하는 안만 편집기로 가져가거나 바로 재검사할 수 있습니다.

우선순위 비교와 별도로 `예산 구간 3안 비교`는 같은 사용 목적·성능 기준·저장 조건을 유지하면서 목표 예산의 약 80% `절약형`, 100% `목표 예산`, 120% `여유형`을 독립적으로 생성합니다. 각 구간의 목표 금액·실제 예상 합계·예산 여유/초과·호환 상태·분석 점수와 CPU·GPU·RAM·PSU 구성을 한 표와 카드로 보여주며, 한 구간이 실패해도 다른 구간과 실패 사유를 숨기지 않습니다. 현재 견적은 자동으로 바꾸지 않고 사용자가 선택한 구간만 편집기·즉시 검사·새 견적으로 저장할 수 있습니다. 파생 예산은 1만원 단위로 반올림하지만 입력한 목표 예산 구간은 그대로 보존합니다.

예산 구간 생성이 실패한 경우 해당 카드에는 서버가 반환한 후보 풀·요청 조건·실패 facts와 권장 조건 완화를 함께 표시합니다. 성공한 구간만 인접 예산 diff를 계산하며, 실패한 구간을 추정값으로 채우거나 인접 구간의 구성 변화로 오해하지 않습니다.

예산 구간 비교에는 분석 점수가 2개 이상 확인될 때 `예산별 카탈로그 분석 지수 추이`도 표시합니다. 예산에 따라 실제로 생성된 점수만 점으로 연결하고, 중간 구간이 실패하거나 분석 점수가 없으면 선을 끊어 값을 추정하지 않습니다. 이 그래프는 실제 FPS·체감 성능이 아닌 0~100점 카탈로그 분석 지수입니다.

새 예산 snapshot에는 범주별 표시명뿐 아니라 target 구성의 실제 partId·수량·M.2 배치를 보존해 버전별 부분 병합에 사용할 수 있습니다. 서버는 selection의 부품 ID·수량·주변 부품 연결·M.2 배치 형식을 다시 검증하며, 구형 snapshot처럼 selection이 없는 버전은 부분 병합에서 제외합니다. 부분 병합은 범주별로 버전을 선택해 현재 카탈로그 견적을 만들고, 섞인 메인보드·메모리·저장장치의 새 위험을 전체 호환성 재검사로 확인하도록 안내합니다.

부분 병합은 적용 전에 `부분 병합 조합 미리 검사`를 실행합니다. 미리 검사는 현재 견적·공유 snapshot을 바꾸지 않고 전체 호환성 엔진의 상태·예상 합계·차단·주의·확인 필요·대표 finding을 표시합니다. 범주 선택을 바꾸면 이전 미리 검사 결과와 적용 버튼을 폐기하며, 새 조합을 다시 검사한 뒤에만 편집기 적용·즉시 검사를 허용합니다.

비교 결과는 화면에 표시된 성공·실패·인접 구간 차이를 같은 snapshot으로 `비교 복사`하거나 CSV·JSON으로 저장할 수 있으며, 실패 구간은 임의의 합계·구성으로 채우지 않고 서버 오류와 diagnostics를 그대로 보존합니다.

예산 구간 비교 결과는 `공유 링크`로 서버 snapshot에도 저장할 수 있습니다. 공유 저장은 30일 만료와 owner token을 사용하고, 서버가 예산 구간 ID·상태·금액 범위·부품 범주·인접 diff·생성 조건을 다시 검증합니다. 공개 응답에는 owner token을 포함하지 않으며, 공유 당시 카탈로그 기준 시각과 현재 기준 시각이 달라지면 `공유 후 카탈로그 갱신`으로 표시하되 저장된 결과를 임의로 재계산하지 않습니다. `/budget-ladder/{id}`는 생성 조건·3개 구간·실패 diagnostics·예산 증액 diff를 읽기 전용으로 보여주고, 공유받은 사용자는 현재 카탈로그 기준으로 세 구간을 다시 생성해 당시 결과와 합계·위험·분석 점수·부품 변경을 비교할 수 있으며 같은 텍스트·CSV·JSON export를 사용할 수 있습니다. 재생성 성공 결과는 원하는 구간만 `현재 결과로 편집기` 또는 `현재 결과 바로 검사`로 이어갈 수 있고, `새 snapshot으로 공유`하면 원본 링크를 덮어쓰지 않은 별도 30일 링크를 발급해 최신 결과를 보존합니다. 새 snapshot은 원본과 `v2`, `v3` 형태의 lineage를 유지하며 공유 화면에서 같은 이력의 이전 버전으로 이동할 수 있고, 최대 3개 버전을 선택해 생성 조건·카탈로그 기준·금액·위험·분석·부품을 한 표에서 비교할 수 있습니다. 버전 비교표는 기준 열 이후 실제 결과가 달라진 셀만 강조하고, 변경된 결과가 하나도 없으면 `변경된 항목만 보기`를 비활성화합니다. 선택한 버전 사이의 예산 구간별 예상 합계와 카탈로그 분석 지수 추이는 실제 확인값만 연결한 두 그래프로 표시하며 누락값은 선으로 추정하지 않습니다. target 구성의 selection payload가 있는 버전은 범주별 `vN 적용 버전`을 선택해 부분 병합 후 편집기·즉시 검사로 연결할 수 있고, selection이 없는 구형 버전은 병합 후보에서 제외합니다. 저장된 구형 snapshot에서 생성 조건의 예산이 절약형 값으로 남아 있더라도 서버가 target 구간 예산으로 정규화해 재생성 기준을 복구합니다.

자동 구성 단일 초안과 3안 비교의 각 성공 결과는 `새 견적으로 저장`할 수 있습니다. 저장할 때 생성 조건·우선순위·목표 예산·게이밍 해상도·구매 조건을 함께 보존하고, 현재 견적을 덮어쓰지 않은 별도 공유 견적으로 열어 현재 카탈로그 기준 재검사를 수행합니다.

자동 구성 결과는 최종 선택안에 한해 카탈로그 상대 성능 점수, 분석 근거 수준, CPU·GPU 밸런스, 확장성 병목과 다음 확인 순서를 함께 보여줍니다. 내부 후보 탐색용 호환성 평가는 기존처럼 가볍게 유지하고, 분석은 최종안에만 별도로 계산합니다. 이 점수는 실제 FPS·렌더링 벤치마크가 아니라 현재 카탈로그의 확인된 스펙을 같은 범주 안에서 비교한 참고 지수입니다.

자동 구성 3안 비교에는 `자동 구성 빠른 선택` 요약을 추가해 호환 우선·가격 우선·분석 점수 우선 후보를 생성에 성공한 안들 사이에서 독립적으로 계산합니다. 일부 우선순위 생성이 실패하면 성공한 안만 기준으로 제한해 표시하고, 가격·분석 데이터가 없는 안은 해당 기준의 확정 후보로 사용하지 않습니다.

자동 구성 요청이 현재 조건으로 실패하면 `426` 응답의 `recoveryOptions`에 실제로 다시 생성 가능한 완화안만 담습니다. 각 옵션은 변경할 조건, 재생성 요청값, 예상 합계, 예산 상태, 호환·확인 필요 상태를 포함하며, 클라이언트는 이를 검증한 뒤 사용자가 선택한 옵션만 다시 요청합니다. 실패한 새 요청이 이전에 성공한 초안을 화면에 남겨 잘못 적용하지 않도록 새 단일안 요청 시작 시 이전 초안을 비웁니다.

자동 구성의 필수 스펙은 요청 조건에 따라 계산합니다. HDD를 요청하지 않은 경우 케이스의 HDD 베이 수가 원문에서 확인되지 않아도 GPU 장착 길이(외장 GPU를 요청한 경우), CPU 쿨러 높이, 메인보드 폼팩터, PSU 장착 길이·폼팩터처럼 실제 선택에 필요한 값이 모두 확인되면 후보로 사용할 수 있습니다. HDD를 요청하면 케이스 HDD 베이 수까지 확인되고 요청 개수를 수용해야 하며, 외장 GPU를 요청하면 GPU 허용 길이도 확인되어야 합니다. 데이터 품질이 `incomplete`라는 전체 라벨만으로 후보를 일괄 제외하지 않고, 해당 시나리오에 불필요한 누락 필드는 허용하되 최종 호환성 재검사에서 새로운 확인 필요나 차단 오류가 생기지 않는지 다시 확인합니다.

`POST /api/builds`는 사용자가 지정한 이름과 함께 핵심 부품·주변 부품 선택, 사용 목적·우선순위·예산·구매 조건을 저장합니다. 공유 링크 유효기간은 `expiresInDays: 7|30` 또는 생략(무기한)으로 지정하며, 잘못된 기간은 저장 전에 차단합니다. 공유 링크를 다시 열면 저장 당시 추천 기준으로 재검사해 같은 비교 결과를 재구성합니다. 기존 저장 데이터에 추천 기준이 없으면 현재 기본값을 사용합니다. 결과 화면과 저장 다이얼로그에는 링크 만료 시각도 표시합니다.

일반 사용자의 저장 견적 히스토리는 브라우저에 보관한 공유 ID만 `GET /api/builds?ids=id1,id2`로 조회합니다. ID 없이 전체 저장 견적 목록을 요청하는 `GET /api/builds`는 관리자 인증이 켜진 환경에서 관리자만 사용할 수 있어, 다른 사용자의 저장 구성 목록이 일반 화면에 노출되지 않습니다. 공유 링크 상세 `GET /api/builds/:id`는 링크를 가진 사람에게 공개되지만 만료된 견적은 404로 차단합니다.

공개 견적 생성은 IP 기준 분당 20회, 저장 견적·관심 목록 공유 링크 조회는 IP 기준 분당 120회로 제한합니다. 최대 20개 견적을 한꺼번에 평가하는 전체 건강 점검은 별도의 IP 기준 분당 20회 제한을 적용합니다. 제한에 도달하면 `429`와 `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`을 반환합니다. 현재 limiter는 단일 프로세스 메모리 보호 계층이므로 여러 서버 인스턴스를 운영할 때는 Redis 등 공유 저장소 기반 limiter로 교체해야 합니다.

견적을 새로 저장하면 서버는 생성자에게만 한 번 반환하는 owner token을 발급합니다. 브라우저는 이 토큰을 공유 견적 ID와 함께 로컬에 보관하고 결과 화면에 `공유 링크 취소`를 표시합니다. 취소 요청은 `X-Share-Owner-Token` 헤더의 해시가 저장된 값과 일치할 때만 허용하며, 서버 파일·PostgreSQL에는 원문 토큰이 아니라 SHA-256 해시만 저장합니다. 토큰이 없는 기존 견적은 관리자만 취소할 수 있습니다.

저장 견적 히스토리에서도 owner token이 있는 내 견적에는 공유 링크 취소를 표시합니다. 다른 사람이 공유 링크를 열어 만든 히스토리 항목이나 owner token이 없는 legacy 견적에는 취소 동작을 노출하지 않습니다.

저장 견적에서 두 항목을 비교하면 저장 시점의 구성·금액뿐 아니라 현재 카탈로그 기준으로 두 견적을 각각 읽기 전용 재검사합니다. 현재 호환 상태, 차단·주의·확인 필요 개수, 상대 분석 점수, 재검사 총액과 엔진 시점을 나란히 표시하며, 한 견적의 재검사 실패가 다른 견적의 결과를 가리지 않습니다. `현재 기준 다시 검사`는 저장된 구성과 현재 편집기를 변경하지 않습니다.

저장 견적 화면을 열면 `/api/builds/check-preview`가 브라우저에 기억된 견적 ID를 최대 20개까지 한 번의 요청으로 같은 현재 카탈로그 기준에서 읽기 전용 점검합니다. 각 견적은 현재 차단 오류와 확인 필요, 마지막 검사 대비 위험 증감, 가격·카탈로그·검사 엔진 변화에 따라 `구매 전 수정 필요`·`확인 필요`·`상태 개선`·`정보 변화 감지`·`첫 기준 기록 권장`·`현재 상태 안정`으로 분류됩니다. 일부 견적이 만료되거나 검사에 실패해도 다른 견적 결과와 전체 요약은 유지합니다. 이 전체 점검은 저장 데이터와 공유 링크를 수정하지 않으며, 실제 검사 이력 기록은 해당 브라우저가 owner token을 가진 견적에서만 기존 소유자 인증 API로 실행합니다.

저장 견적 화면의 `먼저 확인할 견적` 보드는 저장 당시 스냅샷·현재 전체 점검·최대 20회 검사 이력을 합쳐 차단 100점·주의 10점·확인 필요 1점의 정렬용 위험 점수를 계산합니다. 즉시 확인·검토 필요·점검 실패를 먼저 올리고, 변화 감지·첫 기준·안정 견적을 뒤에 배치하며, 최근 위험 점수 추이·주요 finding·직전 기록 대비 가격 변화를 함께 보여줍니다. 보드 필터와 `견적 보기`는 저장된 구성이나 공유 링크를 수정하지 않고 전체 검사 결과로 이동합니다.

우선 확인 보드의 `다음 조치 분석`은 선택한 저장 견적 하나에 대해서만 기존 전체 호환성 엔진과 수리 플랜을 추가 계산합니다. 가장 먼저 바꿔 볼 카테고리·후보 부품·수량 변경, 줄어드는 차단 오류 수, 남는 위험, 적용 후 금액을 최대 3개 변경 내역으로 요약하며, 안전한 수리 플랜이 없으면 분석 엔진의 다음 행동으로 내려갑니다. 이 계산은 저장 데이터와 공유 링크를 쓰지 않고, 모니터 결과가 새로 도착하면 이전 조치 결과를 폐기해 오래된 추천을 남기지 않습니다.

`페이지를 열어 둔 동안 자동 점검`을 켜면 5·15·30분 주기로 현재 보이는 저장 견적을 다시 점검합니다. 브라우저 탭이 보이는 동안에만 요청하며 설정은 해당 브라우저에 복원됩니다. 점검에서 구매 전 수정·확인 필요·상태 개선·가격/판정 정보 변화·첫 기준 필요·개별 조회 실패가 새로 감지되면 `저장 견적 알림함`에 최대 50건을 기록합니다. 검사 시각만 달라진 동일 신호는 같은 fingerprint로 중복 생성하지 않고, 읽음과 지우기 상태도 브라우저에 보관합니다. 지운 신호는 상태 fingerprint가 실제로 달라지기 전까지 다시 나타나지 않습니다. 이 알림함은 외부 푸시·이메일이나 서버 검사 이력이 아니며 저장 견적 데이터와 owner token을 수정하지 않습니다.

저장 견적 알림 상태는 최상위 앱에서 관리해 다른 화면으로 이동해도 상단 `저장 견적` 메뉴의 미읽음 배지가 유지됩니다. 같은 origin의 다른 탭에서 알림을 읽거나 지우면 storage 이벤트로 현재 탭의 배지도 동기화합니다. 알림함은 `전체`·`미읽음`·`즉시 확인`·`정보 변화` 필터와 각 필터의 건수를 제공하며, 현재 브라우저 기록에 남아 있는 견적 알림은 `견적 보기`로 바로 열 수 있습니다. 알림에서 견적을 열면 해당 알림만 읽음 처리되어 전역 배지에 즉시 반영됩니다. 저장 견적의 전체 추천 재계산이 길어질 때는 `불러오는 중` 상태와 즉시 토스트를 표시하고 다른 열기·기록·취소 동작을 잠시 차단해 중복 요청을 막습니다.

알림함의 `브라우저 데스크톱 알림`은 기본적으로 권한을 요청하지 않으며, 사용자가 `브라우저 알림 허용`을 직접 눌렀을 때만 브라우저 권한 요청을 시작합니다. 허용 후 `사용 중`이면 페이지가 열려 있고 새 미읽음 알림이 들어오는 순간 기기 알림을 한 번 표시하며, 알림 ID를 최대 100개까지 delivery ledger로 기억해 새로고침·polling 반복으로 중복 발송하지 않습니다. 권한 거부 상태는 브라우저 설정에서 다시 허용해야 하며, 이 기능은 브라우저가 완전히 종료된 동안의 Web Push가 아니라 foreground 알림입니다.

현재 브라우저 저장 견적 목록에서 사라진 과거 알림은 미읽음이거나 점검 실패일 때까지는 보여 주되, 사용자가 읽은 뒤에는 목록에서 자동으로 접습니다. 알림 record 자체를 임의 삭제하지 않아 같은 fingerprint의 dismissal·읽음 상태는 계속 보존합니다.

owner token이 있는 저장 견적은 `서버 백그라운드 점검`을 1시간·6시간·24시간 주기로 구독할 수 있습니다. owner token이 없는 legacy·공유 견적에는 제어를 노출하지 않고, 새로 저장한 내 견적부터 사용할 수 있다는 읽기 전용 안내만 표시합니다. `GET/PUT /api/builds/:id/monitor`, `POST /api/builds/:id/monitor/run`, `POST /api/builds/:id/monitor/alerts/read|dismiss`는 정확한 `X-Share-Owner-Token` 또는 명시적으로 활성화된 관리자 인증만 허용합니다. 관리자 인증이 꺼진 환경을 암묵적 admin으로 취급하지 않으며 무토큰 요청은 `401`입니다. 서버는 마지막 성공 snapshot·시도/성공/다음 예정 시각·최근 오류·최대 50개 알림을 `saved_builds.monitor_state` JSONB 또는 file fallback의 내부 record에 저장하고, 공개 공유 응답에서는 monitor state와 owner hash를 제거합니다. 구독을 처음 켜면 즉시 한 번 점검하고 이후 process scheduler가 매분 due 상태를 확인해 한 tick에 최대 5개를 순차 평가합니다. 전역 카탈로그 시각이나 엔진 버전만 바뀌고 실제 호환 상태·위험 수·가격·finding이 같으면 새 서버 알림을 만들지 않습니다. 같은 견적의 수동 실행과 scheduler 실행은 process-local job lock으로 합쳐 중복 평가를 막습니다. `BUILD_MONITOR_SCHEDULER_ENABLED=false`로 scheduler를 끌 수 있으며, 다중 서버 운영에서는 중복 계산 방지를 위한 PostgreSQL/Redis 기반 분산 lease가 추가로 필요합니다.

앱이 실행 중일 때도 owner 견적의 서버 모니터 상태를 초기 로드하고 5분마다 보이는 탭에서 읽기 전용으로 동기화합니다. 따라서 사용자가 저장 견적 화면에 있지 않아도 서버가 생성한 알림이 상단 미읽음 배지에 반영됩니다. 동기화 중 한 견적이 실패해도 다른 owner 견적과 기존 로컬 알림은 유지하며, 요청이 겹치면 하나의 동기화 작업만 실행합니다.

견적별 서버 알림 정책은 `위험 악화만`·`위험 변화`·`모든 변화`로 선택합니다. 위험 악화만은 차단 오류와 점검 실패, 위험 변화는 여기에 확인 필요 변화까지, 모든 변화는 개선·가격·판정 정보 변화와 첫 기준 필요까지 포함합니다. 정책은 서버 `monitor_state`에 저장되고 scheduler·수동 점검·owner 브라우저 알림 병합에 같은 기준을 사용합니다. 정책을 모르는 legacy monitor state는 기존 동작을 보존하도록 `모든 변화`로 해석합니다.

공유 견적을 열지 못하면 이전 세션의 다른 검사 결과를 재사용하지 않고 전용 오류 화면을 보여줍니다. 링크가 만료·삭제되었거나 일시적인 API 오류인 경우 메시지와 `다시 시도`, `홈으로` 동작을 분리해 제공합니다.

결과 화면과 저장 견적에는 핵심 부품 금액·주변 부품 금액·전체 금액을 분리해 표시합니다. 가격을 확인하지 못한 영역은 금액을 확정하지 않고 `가격 확인 필요`로 유지합니다.

전체 호환성 API의 반복 계산은 서버 process-local 결과 캐시를 사용합니다. 캐시는 5분 TTL·최대 40개 LRU이며, 동일한 입력의 동시 요청은 한 계산으로 합칩니다. 캐시 키에는 부품 선택·수량·M.2 배치·추천 기준·엔진 버전·핵심 카탈로그 갱신 시각·주변 부품 갱신 시각·catalog runtime revision을 포함해 가격·override·주변 부품 변경 뒤 오래된 결과를 재사용하지 않습니다. 응답은 브라우저·프록시가 저장하지 않도록 `Cache-Control: no-store`를 사용하고 `X-PC-Supporter-Compatibility-Cache`에 `MISS`·`HIT`·`COALESCED`를 표시합니다. `X-PC-Supporter-Compatibility-Checked-At`은 실제 계산 결과의 검사 시각이며, `HIT`도 새 시각으로 위장하지 않습니다. 캐시는 서버 재시작 시 비워지며, 다중 서버 인스턴스에서는 각 process가 별도 캐시를 가지므로 공유 캐시가 필요하면 Redis 등으로 교체해야 합니다.

관리자는 `/api/admin/monitor/status`에서 서버 monitor scheduler의 활성 여부·배치 상한·최근 lease backend·획득/skip/완료 시각·처리 건수·최근 오류와 호환성 결과 캐시의 size·in-flight·hit·miss·coalesced·eviction 통계를 확인할 수 있습니다. 이 운영 응답은 `requireAdmin` 뒤에 있으며 일반 공유 사용자에게 노출하지 않습니다. PostgreSQL 환경의 lease는 `pg_try_advisory_lock` 세션 락을 사용하고, JSON fallback은 공유된 `data/saved-build-monitor.lease`의 원자적 생성과 2시간 stale 복구를 사용합니다. 단일 process 내부 scheduler lock과 별도로 cross-process lease를 획득하지 못하면 해당 tick은 정상 skip합니다.

결과 화면의 구매 목록은 선택된 핵심 부품과 주변 부품을 분리해 수량·단가·항목 합계를 보여줍니다. 목록을 텍스트로 클립보드에 복사하거나 CSV로 저장할 수 있으며, 가격 미확인 항목은 합계에 0원으로 포함하지 않고 `가격 확인 필요`로 남깁니다. CSV에는 허용된 원문 링크를 포함한 구매 행을 스프레드시트에서 다시 사용할 수 있는 형태로 내보내고, 핵심·주변·전체 금액 요약은 화면에서 별도로 표시합니다.

검사 결과는 견적 입력과 추천 기준의 지문을 함께 기억합니다. 검사 후 부품 수량·선택·M.2 슬롯 배치·내장 그래픽 설정 또는 추천 프로필·우선순위·예산·구매 조건을 바꾸고 이전 결과로 돌아오면, 오래된 판정·대체 후보·업그레이드 추천을 현재 입력에 섞지 않고 `현재 구성은 아직 검사되지 않았습니다` 화면에서 재검사를 요구합니다. 네트워크 오류가 나도 마지막 성공 결과는 보존하되, 변경된 입력에 대한 판정으로 오인하지 않도록 분리합니다.

변경 이력에서는 부품·수량·추천 기준이 바뀐 시점의 이전 입력을 최대 20개까지 보존합니다. `이전 구성 복원`을 누르면 선택 부품과 추천 기준을 함께 되돌리고 현재 카탈로그 기준으로 자동 재검사하며, 복원 전 판정이나 추천을 그대로 재사용하지 않습니다.

결과 화면의 `리포트 복사`는 검사 판정·카운트·추천 기준·선택 구성·가격 요약·판정 사실·대체 후보·다음 행동·데이터 경계를 사람이 읽을 수 있는 텍스트로 내보냅니다. `JSON 저장`은 검사 입력과 엔진 결과를 버전이 있는 JSON envelope로 저장합니다. 오래된 결과 상태에서는 현재 입력과 다른 리포트를 만들지 않도록 두 내보내기 동작을 제공하지 않고 먼저 재검사하게 합니다.

결과의 `부품 정보 신뢰도`에서 스펙 부족·가격 미확인·갱신 권장 상태인 다나와 핵심·주변 부품은 `원문 다시 확인`으로 상세 페이지를 다시 가져올 수 있습니다. 핵심 부품은 `/api/parts/:id/refresh`, 주변 부품은 `/api/accessories/:id/refresh`를 사용해 각각의 파서와 저장소 경계를 유지합니다. 서버는 HTTPS 다나와 상품 URL과 저장된 상품 코드를 대조하고, 한 번에 한 상품만 제한적으로 요청하며, 기존 live 데이터보다 부족한 응답이나 스펙 원문이 없는 응답은 저장하지 않습니다. 성공한 갱신은 같은 파서와 저장소를 거친 뒤 현재 견적을 자동 재검사하고, 같은 상품의 연속 요청은 cooldown으로 제한합니다. 관리자 비밀번호가 설정된 환경에서는 이 데이터 변경 API도 관리자 인증을 요구합니다.

재확인 대상이 여러 개이면 `재확인 대상 n개 모두 확인`으로 최대 12개를 순차 처리할 수 있습니다. 각 상품의 성공·실패를 분리해 처리하고, 일부 상품만 갱신되어도 현재 견적은 마지막에 한 번만 재검사합니다. 모든 요청이 실패하면 기존 검사 결과를 새 결과로 바꾸지 않으며, 성공 항목이 있을 때만 갱신 요약과 재검사를 진행합니다.

원문 재확인 성공·실패 이력은 `data/catalog-change-log.json`에 최대 1,000건까지 저장합니다. 데이터 센터의 `최근 원문 갱신 이력`에서 핵심·주변 부품을 구분하고, 이전·현재 품질, 누락 필드, 가격 전후 값과 증감, 변경된 스펙 영역을 확인할 수 있습니다. 조회 건수를 최근 24·50·100건으로 바꾸고 한국 시간 기준 시작일·종료일을 지정해 기간을 좁힐 수 있으며, 현재 필터 결과를 CSV 또는 버전이 있는 원본 JSON으로 저장할 수 있습니다. 가격이나 스펙이 변하지 않은 재확인도 값 변화 없음으로 기록해 마지막 확인 시점을 추적합니다.

핵심·주변 전체 크롤링도 작업 완료 시 전후 카탈로그를 비교해 가격·데이터 품질·누락 필드·원문/정규화 스펙이 달라진 기존 상품만 같은 로그에 요약 기록합니다. 이미지 URL만 바뀐 경우나 새로 발견된 상품은 의미 있는 기존 상품 변경으로 세지 않으며, 크롤링 상태·manifest에는 확인 상품 수, 변경 상품 수, 가격·품질·누락·스펙 변화 건수를 별도 summary로 남깁니다. 드라이런에서는 카탈로그와 변경 로그를 쓰지 않습니다.

변경 로그는 데이터 센터에서 전체·핵심·주변 부품 범위, CPU·GPU·RAM 등 카테고리, 가격 상승·하락·신규 확인·품질 개선·품질 저하·누락 감소·누락 증가·스펙 변경·벤치마크 보강 유형으로 즉시 필터링할 수 있습니다. 현재 조회 결과를 기준으로 각 변화 유형의 건수를 별도 요약하고, 품질 저하·누락 증가에는 주의 배지를 표시합니다. 가격을 확인하지 못한 기록은 가격 방향 통계에 포함하지 않으며, 선택한 조건에 맞는 기록이 없을 때는 원본 이력을 지우지 않고 필터 초기화 상태를 안내합니다.

우선 확인 큐는 품질 저하·누락 증가·가격 상승·가격 신규 확인을 운영 위험도순으로 정렬합니다. 품질 저하는 100점, 누락 증가는 90점, 가격 상승은 50점, 가격 신규 확인은 20점이며, 단순 스펙 변경은 작업 큐를 오염시키지 않습니다. 큐와 카테고리 필터는 현재 날짜 조회 범위 안에서만 계산됩니다.

변경 기록의 `상세 비교`를 열면 이전·현재 가격, 품질, 누락 필드, 변경 영역을 나란히 확인할 수 있습니다. 같은 부품이 현재 조회 범위에 여러 번 등장하면 갱신 시각과 변경 영역을 타임라인으로 표시해 기록 간 이동을 지원합니다. 로그에 저장되지 않은 값을 화면에 추정해 표시하지 않습니다.

결과 화면의 대체 부품·업그레이드 조합·수리 플랜은 적용 전에 공통 변경 미리보기를 거칩니다. 현재 구성과 변경 예정 구성의 부품·수량·M.2 배치·그래픽 출력 차이를 확인한 뒤 사용자가 승인해야 전체 호환성 재검사를 실행합니다. 취소하면 현재 선택과 마지막 검사 결과를 그대로 유지하며, 승인 후 재검사에 실패해도 현재 선택 상태를 임의로 바꾸지 않습니다.

결과 화면의 `구매 전 실행 체크리스트`는 엔진이 만든 차단·주의·확인 필요 finding과 사용자가 직접 확인해야 하는 QVL·BIOS·실물 간섭·케이블·M.2·POST·판매자 조건을 별도 항목으로 관리합니다. 항목은 전체·엔진 finding·직접 확인 필터로 좁혀 볼 수 있으며, 체크 상태는 현재 견적 입력·카탈로그 기준·엔진 버전에 묶인 브라우저 저장값입니다. 부품·수량·추천 기준·카탈로그 기준이 바뀌면 이전 체크를 재사용하지 않습니다. GPU 물리 검수나 다중 8핀 케이블 근거가 없으면 일반 문구 대신 부족한 근거를 직접 표시하고, `GPU FIT 보기`로 관련 결과 패널에 이동할 수 있습니다. finding 항목은 해당 결과 카드로 이동할 수 있고, 전체 체크리스트는 텍스트로 복사하거나 인쇄할 수 있습니다. 모든 체크를 완료해도 실제 검사에 차단 오류가 남아 있으면 `체크 완료 · 차단 n개 잔여`로 표시해 체크 완료를 호환성 통과로 오해하지 않도록 합니다.

수리 플랜의 `현재와 비교`는 최신 현재 견적과 최신 플랜 적용 결과를 각각 전체 규칙 엔진으로 재검사합니다. 비교표에는 호환 상태·위험 카운트·분석 점수·핵심/주변 금액·카테고리별 부품과 수량·플랜 적용 후 남은 finding을 표시하고, 비교 과정에서 확인된 최신 후보 가격과 이름을 실제 적용 전 변경 미리보기에도 동일하게 사용합니다. 가격이 확인되지 않은 주변 부품은 `없음`과 `가격 확인 필요`를 구분하며, 비교만으로는 현재 견적을 변경하지 않습니다.

결과 화면의 `견적 전체 가격 추적`은 현재 선택된 핵심·주변 부품을 중복 없이 가격 추적 목록에 한 번에 등록합니다. 카탈로그에 없는 항목, 가격 미확인 항목, 이미 추적 중인 항목, 로컬 관심 목록의 50개 한도 초과를 따로 집계하며, 등록 후 목표가·알림 조건은 가격 추적 화면에서 설정합니다.

저장 견적 화면에는 저장하지 않은 `현재 편집기 견적`을 임시 비교 대상으로 선택하는 기능도 있습니다. 현재 견적은 서버에 저장하지 않고 저장 견적과 최대 2개, 또는 저장 견적만 최대 3개를 비교하며, 저장 시점 금액·부품 구성과 현재 카탈로그 재검사 상태·위험 카운트·상대 분석을 같은 표에서 비교합니다. 비교표에는 기준별 결정 요약·전체 순위와 저장 시점·현재 재검사 결과 export도 함께 제공합니다.

저장 견적 비교표의 `비교 결과 빠른 선택`은 현재 카탈로그 재검사가 완료된 견적만 대상으로 `호환 우선`·`가격 우선`·`분석 점수 우선`·`확장성 우선`을 독립적으로 계산합니다. 호환 우선은 차단 100점·주의 10점·확인 필요 1점 위험 점수, 가격 우선은 가격이 완전히 확인된 총액, 분석 점수 우선은 사용 목적별 상대 분석 점수, 확장성 우선은 메모리 용량·슬롯·M.2·SATA·HDD 베이·전력·냉각·GPU/PSU/쿨러 장착 여유를 가중 평균한 정규화 점수를 기준으로 합니다. 확장성은 관련 지표 중 최소 3개가 확인되어야 순위를 계산하고, 데이터가 없으면 기준 미충족 사유를 남깁니다. 같은 패널의 `기준별 전체 순위`는 선택 기준을 바꿔 1·2·3순위와 기준 미충족으로 제외된 견적의 사유까지 보여줍니다. 이 요약은 하나의 정답을 확정하는 기능이 아니라 선택 기준별 결과를 분리해 보여주는 결정 보조입니다.

저장 견적 비교표의 `비교 복사`·`CSV 저장`·`JSON 저장`은 저장 시점 스냅샷과 현재 카탈로그 재검사 섹션을 구분해 내보냅니다. 현재 재검사가 아직 끝나지 않은 값도 임의로 저장 시점 값으로 대체하지 않고 진행 중 상태를 보존하며, export 포맷은 클릭할 때만 lazy load합니다.

견적을 저장할 때 서버는 현재 카탈로그와 규칙 엔진으로 핵심·주변 부품을 다시 평가한 뒤 `checkSnapshot` 요약을 함께 보존합니다. 스냅샷에는 저장 당시 호환 상태, 차단·주의·확인 필요 카운트, 핵심·주변·전체 금액의 확정 여부, 상대 분석 점수·신뢰도, 엔진 버전, 카탈로그 기준 시각이 들어가며 상세 finding이나 owner token은 포함하지 않습니다. 저장 견적을 비교하면 이 기록과 현재 카탈로그 재검사를 분리해서 볼 수 있고, 판정·위험 카운트·가격·엔진·카탈로그 기준의 변화 원인을 `스냅샷 대비 변화`로 표시합니다. 기존 스냅샷 없는 저장 견적도 그대로 열 수 있으며 `검사 기록 없음`으로 표시됩니다.

견적 소유 토큰이 이 브라우저에 있는 저장 견적에는 `현재 검사 기록 추가` 버튼이 표시됩니다. 이 동작은 공유 링크 열람만으로 자동 실행되지 않으며 owner token을 `/api/builds/{id}/check`에 보내 서버에서 현재 카탈로그 기준으로 다시 검사한 뒤 `checkHistory`에 최대 20회를 오래된 순서대로 보존합니다. 카드에는 최근 4회 타임라인을, 비교 화면에는 최신 스냅샷과 현재 재검사 차이를 표시합니다. 타임라인 기록 추가는 구성·공유 링크·owner token을 바꾸지 않고 검사 기록만 갱신합니다.

새로 저장하는 검사 기록에는 규칙별 상세 요약도 포함됩니다. `ruleId`·심각도·제목·메시지·영향 부품과 최대 4개의 판정 사실만 보존하며, actions·대체 후보·전체 finding payload는 저장하지 않습니다. 공유 결과 또는 저장 견적 화면에서 기준 검사와 비교 검사를 선택하면 규칙별 `해결됨`·`새로 발생`·`심각도 변경`·`판정 내용 변경`·`변화 없음`을 확인할 수 있고, 가격·상태·카탈로그 기준 변화도 함께 표시합니다. 구버전 스냅샷에 규칙별 요약이 없으면 상위 요약만 비교하고 상세 diff는 제공하지 않습니다.

상세 diff의 `관측된 카탈로그 변경 근거`는 `/api/builds/{id}/check-causes?from=...&to=...`에서 선택 견적의 부품 ID와 두 검사 시각 사이에 동시에 일치하는 변경 로그만 조회합니다. 가격·원문/정규화 스펙·데이터 품질·누락 필드·벤치마크 보강 영역을 표시하며, 매칭되는 로그가 없을 때는 원인을 변경으로 단정하지 않습니다. 전체 카탈로그 변경 로그 endpoint는 계속 관리자용으로 보호합니다.

규칙별 diff 카드도 before/after finding의 영향 부품 ID를 같은 변경 근거 목록과 다시 대조합니다. 따라서 `RAM 속도`나 `GPU 전원` 같은 특정 규칙 아래에 해당 부품의 가격·스펙·품질 갱신 기록만 `관련 카탈로그 근거`로 붙고, 다른 선택 부품의 변경은 섞이지 않습니다.

새로 생성되는 카탈로그 변경 로그에는 `valueDiffs`도 함께 저장합니다. 가격은 금액, 데이터 품질은 이전/현재 상태, 누락 필드는 이전/현재 필드 목록, 원문·정규화 스펙은 길이를 제한한 원문 JSON으로 `이전 값 → 현재 값`을 보존합니다. 기존 로그에 값 diff가 없으면 화면에서 구버전 값 미보존으로 명시하며 임의의 이전값을 만들지 않습니다.

값 diff를 펼치면 엔진 소비 경로에 근거한 `영향 가능 판정`도 표시합니다. 예를 들어 CPU `PPT/TDP`는 `cpu-motherboard-power`·`cpu-cooler-capacity`·`gpu-psu-power`, 메인보드 `M.2 슬롯`은 `m2-slots`, GPU `길이`는 `gpu-case-length`, PSU `PCIe 보조전원 커넥터`는 `gpu-psu-connector`로 연결됩니다. 가격·데이터 품질·누락 필드는 각각 구매 금액·데이터 신뢰도 영향으로 분리하며, 매핑되지 않은 스펙 키에는 규칙 ID를 발명하지 않습니다. 이 매핑은 `shared/catalog-change-impact.ts`에서 관리합니다.

두 검사 시점을 비교하면 `판정 변화 요약` 카드가 개선·악화·변경·동일 방향을 계산합니다. 전체 판정, 차단·주의·확인 필요 증감, 해결/신규 finding 수, 가격 변화, 카탈로그·엔진 기준 변경을 한 문장 목록으로 묶고, 현재 상태에 맞는 다음 행동을 표시합니다. 이 요약은 실제 스냅샷과 finding diff만 사용하며, 호환성 통과 후에도 제조사 원문과 실제 조립 조건 확인을 안내합니다.

저장 견적 owner token이 현재 브라우저에 있으면 결과 화면의 검사 타임라인에 `현재 기준 재검사·기록` 버튼이 표시됩니다. 이 버튼은 서버에서 저장된 selection을 다시 평가하고 history에 새 스냅샷을 추가한 뒤 현재 열린 타임라인도 즉시 갱신합니다. owner token이 없는 공유 열람자는 버튼을 볼 수 없고 `/api/builds/{id}/check` 호출도 401로 차단됩니다.

검사 결과 상단의 `구매 준비도`는 호환성·가격·데이터 신뢰도·장착·전력·목표 예산 다섯 가지 게이트를 `통과`·`확인 필요`·`구매 보류`·`미설정`으로 요약합니다. 차단 오류가 있으면 구매 보류, 가격·데이터·주의·예산 초과 신호만 있으면 확인 후 구매, 핵심 호환성이 통과해도 GPU·케이스 물리 검수나 다중 8핀 케이블 근거가 없으면 확인 후 구매, 목표 예산을 입력하지 않은 경우에는 예산 게이트를 미설정으로 표시합니다. 실제 BIOS·QVL·온도·소음·배송 조건을 자동으로 보장하는 판정은 아닙니다.

`지금 먼저 확인할 것` 액션 센터는 finding·주변 부품·데이터 freshness·가격·GPU FIT에서 이미 계산된 결과를 다시 판정하지 않고, 차단·확인·조립 전 수동 확인 순으로 최대 6개 행동을 통합합니다. 각 항목의 finding·데이터·GPU FIT·구매 목록 보기 버튼은 원래 근거 위치로 이동하며, 화면의 상세 결과·구매 준비도·체크리스트와 별도의 요약 계층입니다. 체크리스트 항목과 stable ID를 공유하므로 같은 견적의 완료 상태를 `우선 조치 m/n개 완료`로 반영하고, 새 검사·견적 기준 변경 시 기존 체크를 재사용하지 않습니다. 차단 오류가 있고 자동 해결 플랜이 있으면 `최소 변경 수리 플랜 검토`를 가장 먼저 보여주며, 자동 적용하지 않고 수리 플랜 상세로만 이동합니다. 체크리스트는 schemaVersion 1 JSON으로 저장·가져올 수 있으며, 견적 storage key가 다르면 적용을 차단하고 현재 체크리스트에 없는 항목은 무시 수로 안내합니다.

## 다나와 카탈로그 수집

수집기는 다나와 카테고리 목록에서 상품 코드와 상품명을 가져온 뒤, 각 상품 상세 페이지에서 스펙을 보강합니다. 이후 단위·소켓·규격을 표준 필드로 정규화하고, 핵심 부품의 필수 필드가 누락된 상품은 `incomplete`로 저장합니다. 쿨링·방열·저장장치 주변기기·UPS처럼 핵심 호환 판정 대상이 아닌 상품은 별도 액세서리 수집기로 관리하며, 상세 원문이 확인된 상품만 `live`로 표시합니다.

소량 테스트:

```bash
npm run crawl -- --limit 1 --delay 850
```

현재 저장소의 카탈로그에는 9개 카테고리 exhaustive 수집 snapshot이 반영되어 있습니다. 작은 검증을 하거나 가격·스펙을 부분 갱신할 때만 아래 샘플 명령을 사용합니다.

```bash
npm run crawl -- --limit 5 --pages 1 --delay 450
```

페이지와 수집 상품 수를 늘리는 예시:

```bash
npm run crawl -- --pages 3 --limit 40 --delay 850
```

다나와 목록의 `totalProductCount`와 페이지당 본상품 행을 계산해 각 카테고리의 마지막 페이지까지 순회하려면 exhaustive 모드를 사용합니다. 이 모드는 상품 상세까지 성공하고 누락 수가 0일 때만 manifest의 `coverage`를 `complete`로 표시합니다.

```bash
npm run crawl:all
```

현재 저장된 핵심 부품 수와 9개 카테고리별 분포는 관리자 데이터 센터의 `CATALOG SNAPSHOT`과 `/api/meta`에서 동적으로 확인합니다. `data/crawl-manifest.json`은 마지막 수집 작업의 범위·상품 수·coverage를 기록하는 작업 manifest이므로, 샘플 수집 manifest의 상품 수를 전체 카탈로그 수로 해석하지 않습니다. exhaustive 모드는 수집량과 네트워크 상태에 따라 오래 걸릴 수 있으며, 상품 누락·상세 실패가 있으면 작업을 성공으로 표시하지 않습니다. 목록 coverage와 호환 필드 completeness는 별도로 기록합니다.

특정 카테고리만 다시 수집해 가격이나 스펙을 복구할 수도 있습니다.

```bash
npm run crawl -- --category psu --limit 10 --delay 850
```

상세 페이지를 요청하지 않고 목록·변경 요약만 확인하는 dry-run은 `--no-details --dry-run`을 함께 사용합니다. dry-run은 카탈로그와 변경 로그를 저장하지 않고 status/manifest만 갱신합니다.

```bash
npm run crawl -- --category cpu --pages 1 --limit 1 --no-details --dry-run
```

주변 부품은 핵심 카탈로그와 별도의 `data/accessories.json`에 저장합니다. 현재 지원하는 다나와 범주는 저장장치 주변기기, 쿨링팬, 써멀그리스, M.2 SSD 방열판, 그래픽카드 지지대·쿨러, RAM 쿨러, 써멀패드, 팬 허브·컨트롤러, UPS입니다.

주변 부품 샘플 수집:

```bash
npm run crawl:accessories -- --limit 30 --delay 850
```

특정 주변 부품을 전체 목록으로 수집하려면 `--all`을 사용합니다. 기본값은 목록과 상세 페이지를 함께 읽는 모드이며, 상품 수가 많으므로 충분한 지연을 두고 실행합니다. 목록만 먼저 확보하려면 `DANAWA_CRAWL_DETAILS=false`를 지정할 수 있고, 이 경우 상품은 `incomplete`로 남습니다. 이미 수집한 목록의 뒤쪽 상품을 상세 보강하려면 `--offset`과 `--limit`으로 배치를 지정합니다.

```bash
npm run crawl:accessories -- --category cooling_fan --all --delay 850
```

주변 부품도 `--no-details`로 목록-only dry-run을 실행할 수 있습니다.

상세 보강 배치 예시:

```bash
npm run crawl:accessories -- --category storage_accessory --offset 323 --limit 30 --delay 850
```

주변 부품 수집 상태와 마지막 작업 manifest는 `data/accessory-crawl-state.json`과 `data/accessory-crawl-manifest.json`에 기록되고, 범주별 최신 누적 coverage는 `data/accessory-coverage.json`에 유지됩니다. 데이터 센터에서 범주·시작 위치·배치 수량을 지정해 상세 보강 배치, 다음 배치, 미확인 상품 다음 배치, 목록 전체 동기화를 실행할 수 있습니다. `미확인 상품 다음 배치`는 현재 카탈로그에서 이미 `live`인 상품 코드를 제외하고 원본 목록을 필요한 범위까지 순회합니다. 상세 보강 없이 목록만 확보한 전체 수집은 `details=false`로 표시됩니다. 이때 목록 coverage와 저장된 상품의 spec coverage를 별도로 계산하고, 마지막 상세 보강 배치의 offset·처리 건수·미확인 자동 선택 여부는 `lastRun`에 남깁니다. 쿨링팬처럼 원본 AJAX 응답이 반복되면 `missingProducts`에 누락 수를 남기고 전체 성공으로 표시하지 않습니다.

서버는 기본적으로 시작 시 카탈로그 갱신을 한 번 실행하고, 설정된 시간마다 다시 갱신합니다. 비활성화하려면 `DANAWA_CRAWL_ON_START=false`를 사용합니다. 수집기는 요청 타임아웃·재시도·지연을 적용하고 일반 HTTP 요청만 사용하며, 로그인·CAPTCHA·접근 제한 우회 로직은 포함하지 않습니다.

현재 핵심 호환 대상 `data/catalog.json`에는 7,295개가 있고, 저장장치 주변기기와 쿨링·방열·그래픽카드 보조 부품·UPS를 포함한 `data/accessories.json`에는 4,097개가 있습니다. 서비스가 보관하는 레코드는 총 11,392개이며, 주변 부품은 10개 범주로 분류됩니다. 주변 부품 snapshot은 목록 전체 수집과 offset·미확인 자동 선택 기반 단계적 상세 보강으로 구성되어 있으며, 현재 상세 원문 확인 상품은 1,434개, 목록만 확인한 상품은 2,663개입니다. 액세서리는 핵심 부품 필수 스펙을 강제하지 않고 상세 원문·가격·이미지·출처를 기준으로 품질을 표시합니다. 0원·미확인 가격은 정상 가격으로 세지 않으며, 현재 액세서리 가격 확인 상품은 4,091개입니다. 실제 공개 서비스로 운영할 때에는 다나와의 이용 조건·robots 정책·데이터 재배포 범위를 별도로 확인해야 합니다.

핵심 호환 대상은 `data/catalog.json`에 보관하고, 주변 부품은 `data/accessories.json`으로 분리합니다. 두 파일의 레코드는 서로 다른 역할을 가지며, 주변 부품이 SSD·HDD 같은 핵심 선택 후보로 섞이지 않도록 `/api/parts`와 `/api/accessories` 경계를 유지합니다.

PDF는 선택적으로 설치된 `pdftotext`로 본문을 추출해 모델/SKU를 대조하고, 추출기가 없거나 압축·손상·대용량으로 읽지 못하면 URL 접근만 확인한 `수동 확인 필요`로 남깁니다. `persist=false`를 사용하면 결과를 저장하지 않는 미리보기로 점검할 수 있습니다. 비HTTPS·내부/사설 호스트·사용자 인증정보 포함 URL은 차단합니다. 접근 실패·HTTP 오류·모델 식별 불일치·수동 확인 필요 상태는 물리 검수 완료와 구매용 근거에서 자동 통과하지 않습니다. 모델·URL·물리값을 다시 저장하면 이전 source-check 결과는 초기화되므로 다시 점검해야 합니다. 완료 coverage는 필수 물리값을 채우고 제조사 근거가 오래되지 않으며 source-check도 확인된 항목만 포함하며, 저장·삭제·근거 점검 후 관리자 화면에서 다시 조회됩니다.

메모리와 메인보드 원문에서 `EXPO`·`XMP` 프로파일을 정규화합니다. RAM 원문에서 확인되는 킷당 물리 모듈 수, 전체 `CL-tRCD-tRP-tRAS` 타이밍, CAS 레이턴시, 동작 전압도 함께 보존합니다. `32GB(16Gx2)` 킷을 1개 선택하면 슬롯·듀얼채널 계산에는 물리 모듈 2개로 반영하고, 화면에는 킷 수량과 모듈 수를 구분해 표시합니다. CL과 tRCD·tRP·tRAS는 메모리 대체 후보의 유사도와 성능 근거에 반영하고, 속도와 CL로 계산한 `실효 CAS 지연(ns)`도 함께 비교합니다. 실효 지연은 측정값이 아니라 DDR 전송률 기준 `CL×2000/MT/s` 계산값이며, 전체 타이밍과 전압은 상세 스펙·비교표에 표시하되 원문에 없는 값은 추정하지 않습니다. 서로 다른 RAM 상품을 함께 선택하면 속도·CL·전압·프로파일 차이를 혼용 경고로 표시하고, 일부 정보가 없으면 혼용 안정성을 확인 필요로 표시합니다. 혼용 경고의 대체 후보는 현재 RAM 총 용량을 유지하는 데 필요한 킷 수량과 메인보드 슬롯을 다시 계산하며, 후보 API와 선택기에도 추천 킷 수량을 함께 전달합니다. 혼용 후보 카드와 비교표의 가격은 추천 킷 전체 합계로 표시하고 1킷 가격을 보조 정보로 구분합니다. EXPO/XMP 프로파일이 확인된 고속 RAM은 CPU 공식 지원 메모리 속도와 메인보드 상한 중 더 낮은 값을 추가로 확인하고, 프로파일이 없는 RAM에는 CPU 상한을 추정 적용하지 않습니다. 예산 자동 구성도 같은 CPU·메인보드 상한, 프로파일 교집합, 킷 물리 슬롯 기준으로 RAM 후보를 제한하고 생성 후 동일 규칙 엔진으로 재검사합니다. 선택한 RAM 프로파일과 메인보드 지원 프로파일이 겹치면 정상, 겹치지 않으면 물리적 차단이 아닌 주의로 표시하고, 메인보드의 프로파일 정보가 없으면 확인 필요로 표시합니다. 이 검사는 CPU를 아직 선택하지 않은 부분 견적에서도 메인보드와 RAM만으로 먼저 실행됩니다. 최종 오버클럭·부팅 가능 여부는 CPU 메모리 컨트롤러, BIOS 버전, 제조사 QVL을 함께 확인해야 합니다.

결과 화면의 `검사 결과 상세`에는 `전체`·`차단 오류`·`주의`·`확인 필요`·`정보` 심각도 필터와 각 항목 수를 표시합니다. 필터는 원본 판정 순서를 변경하지 않으며, 선택한 범주에 결과가 없을 때는 전체 보기로 복귀할 수 있습니다.

결과 화면의 `인쇄·PDF`는 현재 결과와 선택한 심각도 필터 범위를 브라우저 인쇄 화면으로 보냅니다. 메뉴·수정·적용 같은 조작 요소는 인쇄에서 숨기고, 판정 사실·대체 후보·구매 금액·선택 견적은 남겨 PDF 저장이나 종이 출력에 사용할 수 있습니다.

자동 구성은 CPU 후보를 가격·성능 상위 일부만으로 즉시 축소하지 않고, 먼저 CPU·메인보드 호환쌍을 보존한 뒤 RAM·쿨러·GPU·케이스·저장장치·파워 조합을 정리합니다. 현재 데이터에 호환 가능한 조합이 있는데도 후보 풀 축소 때문에 실패하지 않도록 하며, SATA 포트·케이스 베이처럼 조건상 불가능한 요청은 SSD 용량 완화·HDD 수량 축소·HDD 제외 같은 실제 재생성 가능한 복구안을 함께 계산합니다.

결과 화면의 호환 유지 업그레이드 후보는 서버 추천 순서 외에도 성능 개선 폭·확장성 개선 폭·가격 변화 대비 개선 효율·추가 지출 낮은 순으로 다시 정렬할 수 있습니다. 확장성 개선 폭은 후보를 전체 규칙 엔진에 대입한 뒤 계산한 전후 확장성 점수와 확인된 지표 수를 사용하며, 후보가 새 호환 오류를 만들지 않는 기존 필터는 그대로 유지합니다. 정렬은 이미 계산된 후보만 화면에서 재배치하며 호환성 판정·추천 근거·적용 전 변경 미리보기의 결과는 바꾸지 않습니다. 가격 미확인 후보는 가성비와 추가 지출 정렬에서 임의의 가격으로 계산하지 않습니다.
